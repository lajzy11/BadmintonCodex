# 羽球排點系統 (Badminton Match Master)
## Phase 2 報到工具列與綁定機制互動邏輯規格書

本文件定義「羽球排點系統」在 **Phase 2（現場管理階段）** 的核心操作流程、狀態機轉移、底部浮動工具列（Bottom Toolbar）之動態響應，以及 2-4 人「兩兩綁定」與 5 人以上「群組綁定」之底層演算法評分邏輯。本規格專為觸控裝置（尤其是 10 吋平板橫向主控台）優化，旨在建立極高資訊辨識度與快速流暢的現場操作手感。

---

## 一、 核心 UI/UX 設計原則 (Core Design Principles)

1. **高密度、低視覺複雜度**：
   報到卡片網格（Cards Grid）採用緊湊版面，單一螢幕可直接掃視 30-40 人 [128]。卡片常駐呈現姓名、級數、報到狀態、方案標籤、綁定色條與迴紋針圖示，隱藏付款方式與備註等次要功能，避免卡片被撐大 [128]。
2. **非破壞性點擊 (Non-Destructive Selection)**：
   單點卡片僅執行「選取/取消選取」並呈現反白外框，不直接觸發任何報到或付款變更 [128]。此機制可容許團主現場高頻誤觸，大幅提升容錯率 [128]。
3. **金流與報到完全解耦 (Decoupled Flow)**：
   報到動作不強制綁定付款。系統支援「空值報到」（先報到、後補付款），避免報到人潮在尖峰期因金流核對而卡關 [132]。
4. **解鎖式工具列 (Progressive Disclosure)**：
   僅在「已選人數 > 0」時，螢幕底部才會浮現控制工具列，並依選取人數動態解鎖「一鍵報到」、「群組綁定」等操作 [129]。
5. **大拇指熱區優化 (Thumb Zone)**：
   報到與綁定按鈕固定置於工具列最右側（觸控熱區），點擊區域確保 $\ge 44 \times 44\text{px}$ [129, 170]。

## 二、 報到主視圖：互動流程與浮動工具列響應

### 1. 互動流程圖

```text
               +----------------------------------+
               |      進入「報到與名單」頁面      |
               +-----------------+----------------+
                                 |
                                 v
               +-----------------+----------------+
               |     [球友卡片網格] (未選取狀態)    |
               +-----------------+----------------+
                                 |
                                 |  單點卡片 (可複選)
                                 v
               +-----------------+----------------+
               |     卡片高亮反白，底部浮現工具列    |
               +-----------------+----------------+
                                 |
         +-----------------------+-----------------------+
         |                                               |
         | 已選人數 = 1                                  | 已選人數 >= 2
         v                                               v
+--------+------------------------+     +----------------+------------------------+
| 1. 選取付款方式 (可略過)         |     | 1. 選取付款方式 (可略過)         |
| 2. 點擊 [完成報到]               |     | 2. 點擊 [完成報到] (整批報到)            |
|    - 報到成功, 工具列收合       |     | 3. 解鎖並點擊 [兩兩/群組綁定]           |
+---------------------------------+     +-----------------------------------------+
```

### 2. 底部浮動工具列（Bottom Toolbar）動態解鎖規格

底部工具列會依據當前 `selectedMemberIds.length` 的數量，動態變更按鈕可用狀態（Disabled / Active）：

*   **選取 0 人**：工具列隱藏。
*   **選取 1 人**：
    *   `[完成報到]`：**啟用**。單點直接將球員狀態設為 `checkedIn`，並依據活動設定是否自動帶入 `defaultPaymentMethod`（若有，付款狀態改為 `paid`）[22, 132]。
    *   `[付款方式選擇]`：**啟用**（現金 💵 / LINE Pay 💚 / 轉帳 🏦）。點擊展開快速選單 [119, 129]。
    *   `[關係綁定]`：**停用** (Disabled)。
*   **選取 2 人**：
    *   `[完成報到]`、`[付款方式選擇]`：**啟用**（支援整批報到、整批設定付款）。
    *   `[關係綁定]`：**啟用**。點擊觸發「兩兩綁定（Pairwise Bind）」，此二人下一場強制同隊 [129, 133]。
*   **選取 3~4 人**：
    *   `[完成報到]`、`[付款方式選擇]`：**啟用**。
    *   `[關係綁定]`：**啟用**。點擊觸發「小組同隊綁定」，強制將這 3~4 人排在同一場的同一隊伍中。
*   **選取 5 人以上**：
    *   `[完成報到]`、`[付款方式選擇]`：**啟用**。
    *   `[關係綁定]`：**啟用**。點擊觸發「5 人以上群組綁定」，系統自動產生一個全域唯一的 `bindGroupId` 並分配給這批成員，切換為群組排點算法 [125, 129]。

## 三、 活動成員狀態機（State Machine）與方案時間邊界

在系統中，每位成員的 `attendanceState`（出席與排點狀態）隨活動進行發生互斥轉移。

### 1. 出席狀態機轉換圖

```text
               +-------------------------+
               |  notStarted (時段未開始) |
               +------------+------------+
                            |
                            |  自動/手動時段開啟 [127]
                            v
+--------+     +------------+------------+     +-------------------------+
|  Rest  |<----+      idle (在場等待)     +---->|   timeUp (時段已結束)   |
| (休息中) |     +------+-----------+-----+     +-------------------------+
+---+----+              |           ^
    |                   | 排點上場   | 結算下場
    | 結束休息           v           |
    +------------------> playing (上場中)
```

### 2. 狀態定義與排點池過濾條件

| 狀態名稱 (`attendanceState`) | 定義與說明 | 是否進入排點候選池？ |
| :--- | :--- | :--- |
| **`notStarted`** [125] | 該球員所屬方案（如後半段 10:30 開始）尚未到達 startTime [125]。 | **否**（不參與排點） |
| **`idle`** [125] | 成員已報到，在場邊休息等待系統排點 [125]。 | **是**（主要候選人） |
| **`playing`** [125] | 成員目前正在場上比賽 [125]。 | **否**（比賽中禁止重複排點） |
| **`rest`** [125] | 團主手動將其標記為休息（如暫離、受傷、抽菸）[125]。 | **否**（不參與排點） |
| **`timeUp`** [125] | 該成員方案時段（如早鳥 11:00 截止）已結束 [125]。 | **否**（自動退出排點池） |

### 3. 方案時間截止的「非強制中斷」邊界邏輯 [127]

當開啟 `autoStatusEnabled`（方案時間自動判斷）時，若現在時間已超過球員方案的 `endTime` [127]：

*   **情境 A：球員目前在場下 (`attendanceState === 'idle'`)**
    *   系統立即自動將狀態轉移為 `timeUp`，該球員直接移出排點池 [127]。
*   **情境 B：球員目前在預排區 (`Up-Next Buffer`)**
    *   預排卡片上出現「⏰ 結算後時間到」提示 [22, 127]。
    *   球員仍可跟隨預排上場。
*   **情境 C：球員目前在場上比賽 (`attendanceState === 'playing'`)**
    *   **不中斷比賽**：不強制球員立刻下場，以維持良好打球體驗 [127]。
    *   **延遲轉換**：在球場卡片上標記提示，且實際的狀態轉換延遲到 **團主點擊「結算此場」的當下**。結算完成後，該成員的狀態才轉為 `timeUp`，不再進入下一輪預排 [127]。

## 四、 關係綁定（2-4 人 vs 5 人以上）底層演算法規格

為了解決現場不同規模的綁定需求，並避免大組互綁產生排不進場的邏輯漏洞，系統將關係綁定切分為兩套並存機制 [133]：

### 1. 兩兩/小組綁定 (2-4人，`persistentBinds` 陣列) [133]

*   **適用場景**：情侶搭檔、強強同隊、固定 2-4 人雙打小組 [133]。
*   **資料結構**：在每個成員身上儲存對方的 `ID` 陣列（雙向同步，每人上限與 1 人綁定 [22] 或 4 人互綁 [133]）。
*   **評分加乘 (BoundBonus)**：
    *   當候選 4 人中，同時包含成員 A 與其綁定對象 B 時，該組合的排點總分（Score）獲得極高加分（**+40 分** 或 **+50 分**）[22, 133]。
*   **懲罰限制 (AvoidPenalty)**：
    *   若 A 在候選名單中，但 B 當下不在（例如 B 正在別場打球或尚未報到），系統會對不含 B 的 A 組合套用懲罰，使 A 暫緩上場 [86, 133]。這符合現場「團主幫忙等搭檔下場再一起排」的真實人情味 [86]。

### 2. 多人群組綁定 (5人以上，`bindGroupId` 機制) [133, 134]

*   **痛點背景**：若 5 人以上互綁使用 pairwise 兩兩綁定，因每場上限 4 人，**必定有至少 1 人無法上場**，這會導致傳統演算法施加極重的「缺席懲罰」，結果整組人反而結構性地「永遠排不上場」[133]。
*   **解法資料結構**：群組成員不直接存兩兩 ID，而是由系統指派同一個 `bindGroupId`（例如 `group_east_001`）[125, 134]。
*   **全新評分邏輯（正向加分，無缺席懲罰）** [126, 134]：
    *   演算法計算候選 4 人時，**完全不因「同群組其他人這場沒上場」而扣分** [134]。
    *   改採**正向計數加分**：當候選 4 人中，屬於同一個 `bindGroupId` 的人數越多，分數加乘越高 [134]：
        *   4 人皆同群組：**最高分 (加權最大化)**，直接保送上場 [134]。
        *   3 人同群組：中等加分 [134]。
        *   2 人同群組：輕微加分。
    *   **輪替補位機制**：未被排上的其餘同組成員，靠既有的「等待時間加權 (W1)」在場邊累積權重，自然在下一輪以極高優先權與新組合配對上場，不需額外干預 [134]。
