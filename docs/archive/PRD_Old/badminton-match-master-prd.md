## 1. 產品概述與核心目標

### 1.1 痛點分析
在羽球臨打（零打）活動中，團主或管理者在現場通常面臨極高的營運與認知負荷：
*   **現場排點認知負荷過高**：團主需同時記憶球員級數、性別配對偏好、人際關係綁定（如情侶想同組）與迴避名單（如強手迴避、不愉快摩擦者避開），手動排點耗時且極易遺漏。
*   **場次公平性爭議**：人工排點容易造成部分球友輪空等待時間過長、累計打場次不均，或是對戰實力落差過大（如碾壓局、慘敗局），引發球友抱怨。
*   **財務與報到流程混亂**：報到尖峰期現場收費方式混雜（現金、轉帳、Line Pay），管理者常需一邊用紙本核對報到與收款，一邊下場協調、操作排點，容易發生記錯帳或漏勾報到的情況。
*   **突發狀況應變緩慢**：當現場有人受傷、離場、暫停或臨時報名時，缺乏預排緩衝空間，會導致排點系統無法即時調度，造成現場混亂。

### 1.2 產品核心目標
*   **一站式現場管理**：提供「活動」容器，整合「現場報到」、「財務收費記錄」與「智慧自動排點」於單一控制台。
*   **高直覺 POS 操作體驗**：採用卡牌化與拖曳介面，支援現場快速點擊、長按快捷選單，在平板或電腦上實現極佳的現場管理效率。
*   **智慧公平排點**：利用加權評分演算法，3 秒內算出最佳的下場名單與隊伍組合，提供等待時間與場次次數雙重公平保障。
*   **沉浸式廣播叫號**：整合 Web Speech API 語音廣播佇列，自動進行球場與球友叫號，適應高噪音的場館現場。

## 2. 系統架構與資料模型

系統以單一活動為最小運行容器，全系統內同時僅能有一筆進行中的活動，活動中之成員資料供報到與排點模組共用。

### 2.1 資料結構規格

#### Activity (活動)
*   `id`: `string`
*   `name`: `string` (活動名稱)
*   `startTime`: `DateTime` (活動開始時間)
*   `financeEnabled`: `boolean` (是否啟用帳務記錄與付款功能)
*   `plans`: `Plan[]` (此活動可選之方案陣列)
*   `members`: `ActivityMember[]` (參與此場活動的成員名單)

#### Plan (方案)
*   `id`: `string`
*   `name`: `string` (例如："2小時方案", "3小時方案")
*   `startTime`: `Time` (絕對開始時間，由團主手動設定與維護)
*   `endTime`: `Time` (絕對結束時間)
*   `amount`: `number` (此方案應繳金額)
*   `matchEligible`: `boolean` (是否具備排點資格，預設為 `true`)

#### ActivityMember (活動成員)
*   `id`: `string`
*   `displayName`: `string` (本場活動顯示名稱，現場可編輯，不影響球友跨場原始資料，解決同名同姓混淆)
*   `gender`: `'M' | 'F' | null` (性別)
*   `level`: `number` (級數，區間為 1~10)
*   `planId`: `string` (關聯的 Plan ID)
*   `checkinStatus`: `'notArrived' | 'checkedIn'` (報到狀態：未到／已報到)
*   `attendanceState`: `'idle' | 'playing' | 'rest'`
    *   `idle` (在場等待中)：納入排點候選池。
    *   `playing` (比賽上場中)：已排入球場，暫停計算排點。
    *   `rest` (休息中)：手動切換至休息狀態，暫不納入排點計算。
*   `noShowStatus`: `null | 'pendingCharge' | 'charged' | 'waived' | 'cancelled'` (未到處理狀態，僅在 `checkinStatus === 'notArrived'` 時生效)
*   `paymentStatus`: `'unpaid' | 'paid'` (付款狀態)
*   `paymentMethod`: `string | null` (付款方式，如 'cash', 'coupon', 'linePay', 'transfer')
*   `note`: `string` (備註，用於記錄球友特殊偏好或身體狀況)
*   `matchesCount`: `number` (今日已打場數)
*   `waitCount`: `number` (當前連續輪空/等待場次次數)
*   `boundPlayerId`: `string | null` (雙向唯一的「兩兩綁定」對象 ID)
*   `tempBind1Match`: `string | null` (僅綁一場之搭檔 ID)
*   `tempOppose1Match`: `string | null` (對戰一場之對手 ID)
*   `avoidList`: `string[]` (此球友的迴避名單 ID 陣列)

## 3. 智慧自動排點與關係綁定演算法

### 3.1 加權評分機制 (Weighted Scoring System)
當團主點擊「智慧自動排點」或系統處於自動模式需要補滿球場時，排點引擎會針對所有狀態為 `idle` 的已報到成員，遍歷計算所有可行的 4 人組合（隊伍 A 的 2 人與隊伍 B 的 2 人），計算每組候選組合的綜合權重評分，挑選總分最高（最優）的組合：

$$\text{Score} = W_1(\text{Waiting}) + W_2(\text{Fairness}) + W_3(\text{LevelMatch}) - W_4(\text{Repeated}) + \text{BoundBonus} - \text{AvoidPenalty}$$

#### 權重子項說明：
1.  **等待時間 $W_1$ (Waiting)**：優先安排連續輪空場次最長者上場（權重最高，保障等最久的人優先下場）。
2.  **場數公平 $W_2$ (Fairness)**：優先安排今日已打場數較少者上場。
3.  **級數配對 $W_3$ (Level Match)**：級數落差越小，分數越高。盡量確保對戰兩隊（隊伍 A 與隊伍 B）的平均級數差最小（建議 $\le 1.5$ 級）。
4.  **重複率扣分 $W_4$ (Repeated)**：為避免球友頻繁與相同對手或搭檔重複比賽，排點引擎會直接複用既有的 **歷史對戰紀錄 (Match History Log)** 進行計算。只要候選 4 人組合曾完整出現在某一筆歷史紀錄中（不論當時同隊或對戰），即依重複次數扣分。無須額外新增資料追蹤欄位。
5.  **BoundBonus (關係綁定加分)**：當組合中包含有綁定關係的搭檔時給予大幅度加分。
6.  **AvoidPenalty (關係迴避扣分)**：當組合中包含有迴避關係的球友時給予極大懲罰性扣分（或直接排除）。

#### 客製化設定項目：
*   **權重項目開關**：$W_1$、$W_2$、$W_3$、$W_4$ 分別提供獨立開關。若關閉，則該項權重視為 0 不參與運算。
*   **場次型態偏好**：團主可設定當前排點是否優先促成「男女雙」或「混雙」。

---

### 3.2 關係綁定與迴避邏輯

#### 1. 兩兩綁定 (boundPlayerId) — 雙向唯一綁定
為求操作與演算法設計之簡約、明確，系統維持雙向唯一的兩兩綁定機制，嚴格限制每位成員身上**同時僅能與最多 1 人綁定**。
*   **設定與同步邏輯**：
    *   當 A 與 B 設定綁定時，系統會自動建立雙向關係：A 的 `boundPlayerId` 指向 B，且 B 的 `boundPlayerId` 指向 A。
    *   **舊綁定自動替換**：若 A 原本已與 C 綁定，而團主將 A 改與 B 綁定，系統會自動切斷 A 與 C 的綁定（將 C 的 `boundPlayerId` 設為 `null`），並同步切斷 B 原本的綁定（若有），接著雙向同步建立 A 與 B 的互綁關係。
*   **等候限制說明**：若綁定對象當下不在候選池中（例如搭檔在另一場比賽未結算或暫時休息），系統會對每個不含搭檔的候選組合套用等候懲罰。此時系統會「幫忙等搭檔」，直到搭檔回歸。若等候時間過長，需由團主手動解除綁定。

#### 2. 僅綁一場 (tempBind1Match)
*   下一場強制安排 A 與指定對象同隊，該場次排點完成或上場後，此設定自動解除。重新指定時會自動清除舊搭檔的反向連結。

#### 3. 對戰一場 (tempOppose1Match)
*   下一場強制安排 A 與指定對象在同場對決（隊伍 A vs 隊伍 B），比賽開始或排點完成後自動解除。重新指定時會自動清除舊對象的反向連結。

#### 4. 迴避名單 (avoidList)
*   若 A 將 B 加入迴避名單，則排點引擎計算時，A 與 B **絕對不會出現在同一場球賽中**（不論是同隊或對手）。

#### 5. 關係清除與殘影保護機制
*   當刪除球員、清除特定關係或重設時，系統必須**同步清除其他所有球員身上指向該球員的殘留關係欄位**，避免因單向關係殘影導致排點評分引擎持續套用懲罰或加分而失效。

## 4. 控制台與現場操作管理

本產品之團主控制台以**平板裝置（橫向，約10吋 / ~1024px 寬）**及電腦網頁作為主要優化基準，以適應高密度操作與即時監控情境。手機端則採 Auto Layout 自然往下堆疊，作為行動堪用支援。

### 4.1 版面配置
控制台主畫面採**左右雙欄佈局**：
*   **左欄：球場看板區**
    *   顯示当前所有球場卡片網格（可水平或垂直自然換行，適應 1~6 面場地）。
    *   提供「+ 新增場地」按鈕，點擊可逐一新增場地，新場地預設命名「N 號場」。
    *   每張場地卡片右上角提供「編輯」自訂名稱，以及「刪除」按鈕（**比賽上場中禁止刪除**，且全系統至少保留 1 個場地）。
*   **右欄：預排與球友管理區**
    *   **上方：預排空間 (Preview Zone / Up-Next Buffer)**
        *   展示由排點引擎計算出的「下一組建議上場 4 人卡片」。
        *   支援團主在此手動拖曳卡牌調換成員。
        *   提供「重算預排」按鈕：當有多組候補分數並列最高時，隨機挑選一組，並給予按鈕文字「已重新計算」之輕量化視覺回饋。
        *   提供「一鍵上場 (One-Click Deploy)」按鈕，點擊即將預排區 4 人推送至對應空閒球場。
    *   **下方：球友名單與控制台**
        *   整合「篩選頁籤（全部/已報到/上場中/休息中）」、「快速搜尋欄」與「球友卡牌名單」於單一面板內。
        *   提供「全體報到」、「全體休息」批次快捷鍵。

### 4.2 卡牌長按快捷選單 (Long-Press Quick Actions)
在球場或等待區的名單卡牌上**長按 500ms（或按滑鼠右鍵）**，即可彈出快捷操作選單：
*   **互相綁定**：選擇另一個球友，建立雙向唯一綁定關係。
*   **僅綁一場**：建立單場搭檔關係。
*   **對戰一場**：建立單場對手關係。
*   **迴避名單**：將特定球友加入此人的避開清單。
*   **清除綁定**：一鍵清除此人的所有關係設定，並自動清除指向此人的外部關係。
*   *(註：本系統已徹底移除「減少同組」設定)*

### 4.3 自動模式運作邏輯 (Auto Mode Toggle)
控制台提供一鍵切換的「自動模式」開關：
*   **開啟狀態**：當任一球場比賽結束（點擊「結算此場」）且有空場時，系統會**自動將預排區的人員部署上場**，並**同步觸發叫號語音廣播**，接著自動重新計算補滿下一組預排。
*   **關閉狀態**：比賽結束後，球場釋放為空閒，等待團主手動將預排區上場（此時語音廣播需點擊「叫號」手動觸發）。

### 4.4 語音叫號與廣播系統 (TTS System)
基於網頁 Web Speech Synthesis API 實作：
*   **叫號格式**：「[場地名稱]，請 [球友1]、[球友2]、[球友3]、[球友4] 上場。」
*   **語音引數微調**：
    *   `重複次數`：可選 1 次、2 次、3 次（預設為 2 次）。
    *   `語音速度`：支援 0.5x、0.75x、1.0x（預設）、1.25x、1.5x。
*   **穩定佇列機制 (Queue Management)**：多筆廣播依瀏覽器原生佇列依序播放，不使用強制打斷（`cancel`）函式，避免多場同時結算時語音重疊、卡死或字元截斷。
*   **測試語音**：控制台提供獨立的「測試語音」按鈕，可用於立即中斷播放並快速測試音速與音量，不影響正式比賽的叫號廣播佇列。

### 4.5 比賽歷史與結算 (Match History)
*   **自動時間戳記**：人員排進球場上場時記錄「開賽時間」；點擊「結算此場」時記錄「結束時間」，並自動計算總比賽時長。
*   **比分與勝負編輯**：點擊結算時直接清空場地，**不跳出彈窗阻礙流程**。團主事後若想記錄成績，可手動至歷史紀錄區點擊編輯，支援「僅記錄勝負」或「完整記錄對戰比分」（皆為非必填，彈性留空）。

## 5. 報到與財務稽核模組 (可選)

本模組受活動層級的 `financeEnabled`（啟用帳務記錄）開關控制：
*   **關閉狀態**：所有付款方式、付款狀態、應收金額及財務摘要之 UI 元件完全隱藏，提供更輕量專注的報到介面。
*   **啟用狀態**：解鎖以下報到與收款、帳務稽核流程。

### 5.1 報到主視圖互動流程 (Check-in View)
現場報到採用**高資訊密度之緊湊網格卡片**，結合**底部浮動工具列**，實現快速單手、高效率點擊操作：
1.  **網格卡片**：顯示姓名、級數、報到狀態、方案標籤與兩兩綁定關係圖示。
2.  **單點卡片**：觸發「選取」（可複選，反白顯示），此動作無任何副作用，误觸時可再次單點取消。
3.  **選取 $\ge 1$ 人（底部工具列彈出）**：
    *   顯示已選人數提示。
    *   提供「報到」主要 CTA 按鈕。
    *   提供「付款方式」選擇器（若未選，預設為空，或套用活動預設付款方式。**報到與付款完全解耦，允許空值報到**，避免報到現場受卡住）。
4.  **選取正好 2 人**：底部工具列額外亮起「綁定」按鈕，點擊可直接建立此二人的雙向兩兩綁定關係，並自動替換他們原有的舊綁定。
5.  **長按或點擊詳細**：彈出個人詳細編輯面板，可修改：顯示名稱、所屬方案、金額（自訂例外）、付款狀態與個人備註。

### 5.2 狀態操作與互斥鎖定
球友名單卡片提供「報到」、「休息」、「未到」三顆互斥狀態操作按鈕：
*   **報到**：`checkinStatus = 'checkedIn'`，且 `attendanceState = 'idle'` (進入排點池)。
*   **休息**：`checkinStatus = 'checkedIn'`，且 `attendanceState = 'rest'` (在場不排點)。
*   **未到**：`checkinStatus = 'notArrived'`，此時可進一步在詳細面板設定 `noShowStatus`（待收費、已收費、不予追究、已取消），精確區分爽約、請假或已繳款。
*   **比賽中狀態鎖定**：當球友的 `attendanceState === 'playing'` (正在場上比賽) 時，其狀態按鈕與名單刪除功能將**自動鎖定禁止修改**，必須先點擊「結算此場」釋放球友後方能變更，防止殭屍資料產生。

### 5.3 財務稽核視圖 (Audit View)
*   定位為非現場即時操作的「靜態核對表格」，以條列式表格展示所有成員的完整明細（姓名、級數、方案、報到狀態、付款狀態、付款方式、未到處理與備註）。
*   無常駐的複雜操作按鈕，點擊該欄位文字即可彈出下拉選單微調，保障極佳的閱讀舒適度，便於活動結束後或雙團主對帳時快速審核。
*   **帳務摘要指標**：
    *   出席概況：報名總數、已報到數、未到數。
    *   金額概況：總應收、總已收、總待收。
    *   付款方式統計分布。
    *   「未記錄付款方式」人數提醒，方便團主事後核帳。

## 6. UI 與視覺規範

系統介面設計定位為**「專業信賴感」**的工具後台，嚴格排除大面積飽和漸層、Glassmorphism、大模糊陰影等裝飾性元素，保障在球館各類光源環境下的極佳辨識度。

### 6.1 色彩分工規範
1.  **中性結構色 (視覺基底)**：全站背景、卡片外框、主要文字維持中性灰階 (`slate` 色階)，佔比最大，沉穩專業。
2.  **狀態色 (僅限標示，不可混用)**：
    *   **綠色**：成功或已完成狀態（如：已報到、付款已完成）。
    *   **琥珀色/黃色**：提醒或待處理狀態（如：休息中、帳務待繳納）。
    *   **紅色**：需要注意或錯誤狀態（如：未到、迴避關係）。
3.  **品牌主色 (僅限主要操作 CTA)**：
    *   **定案為藍色**。主要用於「智慧排點」、「一鍵上場」、「報到」、「結算此場」等引導使用者進行下一步的核心操作按鈕。
    *   *註：主要操作按鈕絕不使用綠色，避免與代表「已完成」的綠色狀態色混淆，確保資訊傳達的一致性。*

### 6.2 圓角與陰影
*   **圓角**：全站卡片、按鈕圓角統一收斂在 `rounded-lg` 或 `rounded-md` 級別，避免大圓角造成的可愛玩具感，維持工具軟體之俐落感。
*   **陰影**：僅使用非常輕微、低存在感的細緻陰影來增加漂浮卡片或浮動工具列的層次感，不使用厚重與大範圍模糊陰影。

### 6.3 觸控目標
*   平板與手機之所有可點擊卡牌、動作按鈕、狀態切換器的觸控熱區必須確保 $\ge 44 \times 44\text{px}$，避免臨場手忙腳亂造成誤觸。

## 7. 系統限制與非功能性需求

*   **效能限制**：自動排點引擎在單面場地 4 人組合遍歷時，在常規臨打規模（20-30人）需於 1 秒內完成計算。若規模擴大至 40+ 人（窮舉複雜度 $O(n^4)$），瀏覽器運算可能產生延遲，建議維持在 1-6 面場地、40 人以內使用。
*   **本地持久化機制**：系統無須雲端資料庫。所有活動設定、球友名單、歷史對戰紀錄與收款狀態，均儲存於單機瀏覽器的 `LocalStorage` 中。即便現場網路中斷或重新整理網頁，資料亦不會遺失（不支持跨裝置多工同步操作）。
*   **批次匯入健壯性**：
    *   支援 CSV 與純文字（如 張三/M/5 或 張三/5）的靈活解析。
    *   批次匯入解析前，系統需**自動剝除接龍常見的行首編號**（如 `1.`、`2、`、`3、`），避免編號被誤判為姓名的一部分。
    *   分隔符號同步相容全形符號（如 `／`、`，`、`．`）與半形符號，避免手機中文輸入法自動轉換全形導致解析整行失敗。

## 8. 本版本明確排除之功能 (未來規劃)

為確保核心功能之專注與高可用性，以下項目已明確排除，不在本 PRD 規格範圍內：
*   球友端線上自行預約、線上報名及獨立帳號系統。
*   掃描 QR code 自行認領報到。
*   自訂方案個別修改單人時間/金額之正式 UI 入口。
*   複雜的財務統計圖表與多活動歷史查詢列表。
*   時段結束時自動強制中斷進行中的比賽或強制將人攆下場。
*   多裝置同步或多工作人員協同編輯。
