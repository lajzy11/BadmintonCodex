# 羽球零打系統 — UI / Visual Specification v0.1

> 用途：提供 Gemini Canvas 實作 UI 時的視覺與排版依據。
>
> 本文件與 PRD 搭配使用。PRD 定義「功能與產品行為」，本文件定義「UI 應該如何呈現」。
>
> 核心原則：**功能優先、資訊清楚、操作快速，視覺風格保持乾淨成熟，不為了美觀犧牲辨識度。**

---

## 1. Overall Design Direction

### 1.1 Product Personality

整體應呈現：

- 俐落
- 有效率
- 成熟
- 乾淨
- 直覺
- 輕度運動感

產品應該讓使用者感覺像是一個**成熟的手機 App 工具**，而不是運動品牌展示網站或 AI SaaS 產品。

### 1.2 Design Priority

所有 UI 設計請依照以下優先順序：

1. **資訊辨識度**
2. **操作效率**
3. **資訊層級**
4. **一致性**
5. **視覺美感**
6. **裝飾性**

不得為了視覺效果降低資訊辨識度或增加操作成本。

---

# 2. Information Density

本產品採用**中高資訊密度**。

這裡的「高資訊密度」不是指畫面塞滿資訊，而是：

> 在有限的手機畫面中，盡可能讓使用者快速理解重要資訊，避免為了留白或視覺美感而隱藏、縮小或拆散資訊。

### 原則

- 重要資訊應容易被快速掃讀。
- 不要為了製造大量留白而讓資訊變得過於分散。
- 避免使用過大的標題、Hero 區域或裝飾元素佔據主要畫面。
- 避免讓使用者必須頻繁滑動才能取得基本資訊。
- 資訊可以多，但必須透過清楚的視覺層級組織。

### 特別注意

**高資訊密度 ≠ 高視覺複雜度。**

應透過 Typography、Spacing、Hierarchy、Grouping 解決資訊量，而不是單純縮小文字或增加更多元件。

---

# 3. Layout Direction

### Mobile-first

主要設計基準為手機直式畫面。

### Layout 原則

- 保持清楚且穩定的左右邊界。
- 使用一致的內容寬度與水平 Padding。
- 保持適度留白，但避免過度留白。
- 重要操作應容易在單手操作時找到。
- 不使用大型 Dashboard 式多欄 Layout 作為主要手機介面。
- 不應為了填滿畫面而加入沒有產品價值的 UI 元素。

---

# 4. Information Hierarchy

每個畫面都必須建立清楚的資訊層級。

建議至少區分：

### Primary Information

使用者完成任務時最需要注意的資訊。

例如：

- 球局日期
- 球局時間
- 場次狀態
- 目前人數
- 目前排點
- 核心操作狀態

### Secondary Information

幫助使用者理解情境，但不是第一眼必須注意的資訊。

例如：

- 場館
- 程度
- 費用
- 場地數
- 備註

### Supporting Information

可以降低視覺權重，但仍必須保持良好可讀性。

不得為了視覺簡潔將重要資訊縮小到難以閱讀。

---

# 5. Card Design

本產品**可以使用 Card**。

Card 應被視為「資訊群組與互動單位」，而不是單純的裝飾。

### 適合使用 Card 的情境

例如：

- 一場獨立的球局
- 一個報到區塊
- 一個排點結果
- 一個獨立的功能入口
- 一個需要點擊進入詳細內容的資訊單位

### Card 使用原則

- Card 內資訊應具有清楚的階層。
- 一張 Card 應該代表一個完整的資訊或操作單位。
- 不要將 Card 內的每一個資訊項目再次包裝成小 Card。
- 不要讓所有頁面區塊都變成 Card。
- Card 應以簡潔、輕量為主。

### Card Visual Style

偏好：

- 輕微圓角
- 乾淨邊界
- 輕量視覺層次
- 必要時使用非常輕微的陰影

避免：

- 超大圓角
- 厚重陰影
- 浮誇的立體感
- 漸層 Card
- Glassmorphism
- 過度裝飾

---

# 6. Border Radius

整體偏好：

**輕微圓角、成熟、俐落。**

避免：

- 極端直角造成生硬感
- 超大圓角造成過度可愛或玩具感
- 所有元件都使用相同的大圓角

圓角應該服務於資訊分組與視覺舒適度，而不是成為主要視覺風格。

---

# 7. Shadow

陰影不是主要的視覺語言。

優先使用：

1. Layout
2. Background contrast
3. Border
4. Spacing

建立資訊層次。

必要時可以使用**非常輕微、低存在感的 Shadow**來增加可點擊 Card 或浮動元件的辨識度。

避免：

- 明顯厚重的陰影
- 大範圍模糊陰影
- 透過 Shadow 製造強烈浮空效果

---

# 8. Color Direction

主要色彩方向：

### Option A — Blue

以藍色作為主要品牌色。

傳達：

- 輕盈
- 清爽
- 穩定
- 運動感

### Option B — Green

以綠色作為主要品牌色。

傳達：

- 羽球場地
- 自然
- 活力
- 運動感

目前不需要強制確定最終色碼。

### Color Principle

色彩應該是**輕度運動感的來源之一**，而不是整個 UI 的裝飾。

避免：

- 大面積高飽和色彩
- 大量漸層
- 多色彩同時競爭
- 為了「運動感」而加入過多視覺元素

整體仍應以中性背景與清楚的文字層級為主。

---

# 9. Primary CTA

Primary CTA 必須具有**非常明確的視覺存在感**。

例如：

- 報名
- 確認報到
- 開始排點
- 確認
- 提交

使用者應能快速辨識「現在最重要的下一步」。

### CTA 原則

- Primary CTA 與 Secondary Action 必須具有清楚的視覺差異。
- 不要讓主要 CTA 與普通文字連結具有相同視覺權重。
- 不要為了追求極簡而讓主要操作變得難以辨識。
- Primary CTA 可以使用品牌主色。
- CTA 的尺寸應適合手機觸控，不需要透過巨大尺寸製造存在感。

---

# 10. Interaction Philosophy

使用者應能快速理解：

> **現在在哪裡 → 現在看到什麼 → 下一步可以做什麼**

因此：

- 操作結果需要有清楚的視覺回饋。
- 不應要求使用者猜測哪些元素可以點擊。
- 重要狀態應透過明確的文字、顏色或元件狀態呈現。
- 不要把重要操作隱藏在過多選單或手勢中。
- 互動設計優先考慮現場、快速操作的情境。

---

# 11. Visual Elements to Avoid

請避免以下風格：

- 大量漸層
- Glassmorphism
- 厚重陰影
- 超大圓角
- 過度 Card 化
- 大量插畫
- 過度可愛
- 過度科技感
- AI SaaS 常見的紫色／漸層／玻璃質感視覺
- 大型 Hero Section
- 為了裝飾而增加的圖形
- 資訊過度縮小
- 過度留白導致資訊效率降低
- 看起來像 AI 自動生成的模板網站

---

# 12. Desired Visual Impression

最終 UI 應該接近：

> **成熟的手機 App + 高資訊效率 + 清楚的操作介面 + 輕度運動感**

而不是：

> 運動品牌官網  
> AI SaaS Dashboard  
> Dribbble 展示頁  
> 可愛社群 App  
> 高度裝飾性的 Landing Page

---

# 13. Implementation Constraint for Gemini Canvas

在實作 UI 時：

1. 優先遵循本 UI / Visual Specification。
2. PRD 定義功能，本文件定義視覺與排版方向。
3. 不要自行新增未定義的裝飾性 UI。
4. 不要因為「美觀」而降低資訊辨識度。
5. 不要自行將所有內容 Card 化。
6. 不要自行加入漸層、Glassmorphism、大型插畫或強烈陰影。
7. 不要使用大型 Hero 區域佔據主要手機畫面。
8. 如果功能需求與視覺效果發生衝突，優先維持功能與資訊辨識度。
9. 如果 PRD 沒有指定視覺細節，請遵循本 Specification，而不是自行套用常見 AI SaaS UI 模板。
10. 優先建立一致、可重複使用的 UI pattern，而不是為每個頁面設計不同風格。

---

## Core Principle

> **這是一個讓羽球使用者快速完成事情的工具，而不是一個展示視覺設計的網站。**

> **讓資訊清楚、讓操作快速、讓重要的事情一眼就看得到；美感建立在這些基礎之上，而不是取代它們。**
