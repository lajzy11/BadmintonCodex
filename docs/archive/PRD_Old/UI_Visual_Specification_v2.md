# 羽球零打系統 — UI / Visual Specification v0.2

> 用途：提供 Gemini Canvas 實作 UI 時的視覺與排版依據。
>
> 本文件與 PRD 搭配使用。PRD 定義「功能與產品行為」，本文件定義「UI 應該如何呈現」。
>
> 核心原則：**功能優先、資訊清楚、操作快速，視覺風格保持乾淨成熟，不為了美觀犧牲辨識度。**

---

## 0. 版本異動說明 (v0.1 → v0.2)

v0.1 是初稿方向，部分原則之間存在待釐清的張力；v0.2 是經過討論後的收斂版本，異動如下：

| 項目 | v0.1 | v0.2（本版，已收斂） |
| :--- | :--- | :--- |
| 整體調性 | 俐落／有效率／成熟／乾淨／輕度運動感 | 確認為「**專業信賴感**」（管理後台／工具軟體氣質），非消費性/社群產品的活潑感 |
| 圓角 | 「輕微圓角」（未定義數值） | 明確收斂：現有 `rounded-2xl` 過圓，改用 `rounded-lg` / `rounded-md` 級別 |
| 色彩策略 | 品牌主色（藍/綠二選一）尚未定案，與「色彩僅用於狀態標示」的偏好未整合 | **三層色彩系統定案**（見第 8 節）：中性灰階為主結構、狀態色三色、品牌主色**藍色**專用於主要操作 CTA。不選綠色當品牌主色，避免與「已完成」狀態色混淆 |
| 資訊密度 | 主張全站中高密度，與「稽核頁應舒適留白」的需求表述上有落差 | 收斂為同一套邏輯：密度依情境分層，但差異來自「資訊分組與間距」而非「裝飾性留白」，兩者精神一致，見第 2 節 |
| 主要目標裝置 | 通篇以 Mobile-first／手機直式畫面為基準 | **依角色拆分**（新增第 3.1 節）：團主控制台以**平板**為主要優化基準，手機為相容支援；球友端才適用 Mobile-first 原則 |
| 適用規模 | 未定義 | **新增規模基準**（見第 3.2 節）：1-6 場／20-40 人為舒適使用範圍上下界，2-3 場／16-24 人為視覺尺寸校準的甜蜜點 |

## 1. Overall Design Direction

### 1.1 Product Personality

整體應呈現：

* 俐落
* 有效率
* 成熟
* 乾淨
* 直覺
* 輕度運動感

確認調性定位為**「專業信賴感」**——產品應該讓使用者感覺像是一個**成熟的管理後台／工具軟體**，而不是運動品牌展示網站、AI SaaS 產品、或消費性社群 App 的活潑感。

### 1.2 Design Priority

所有 UI 設計請依照以下優先順序：

1. **資訊辨識度**
2. **操作效率**
3. **資訊層級**
4. **一致性**
5. **視覺美感**
6. **裝飾性**

不得為了視覺效果降低資訊辨識度或增加操作成本。

---

## 2. Information Density

本產品採用**依情境分層的中高資訊密度**，而非全站單一標準。

### 原則

* 重要資訊應容易被快速掃讀。
* 不要為了製造大量留白而讓資訊變得過於分散。
* 避免使用過大的標題、Hero 區域或裝飾元素佔據主要畫面。
* 避免讓使用者必須頻繁滑動才能取得基本資訊。
* 資訊可以多，但必須透過清楚的視覺層級組織。

### 依情境分層（收斂後的具體標準）

* **高密度場域**（球場狀態看板、球友名單網格、Phase 2 報到主視圖）：資訊盡量塞進畫面，減少捲動，符合現場快速操作的需求。
* **低密度場域**（Phase 2 稽核視圖、規則設定面板、活動設定）：資訊分層清楚、閱讀節奏放慢，但**這裡的「留白」是機能性的**（幫助分組、降低核對帳務時的視覺疲勞），不是為了美觀硬塞進去的裝飾性空白（例如大型 Hero 區塊、過大的頁首）。

**特別注意：高資訊密度 ≠ 高視覺複雜度。** 應透過 Typography、Spacing、Hierarchy、Grouping 解決資訊量，而不是單純縮小文字或增加更多元件。

---

## 3. Layout Direction

### 3.1 裝置基準（依角色拆分）

產品服務兩種完全不同的使用情境，**不套用同一套裝置基準**：

| 角色 | 使用情境 | 主要優化基準 | 相容支援 |
| :--- | :--- | :--- | :--- |
| **團主控制台**（Phase 1 球場/排點、Phase 2 報到） | 固定操作平面（桌子、看板架），同時掌握多種資訊的「控制台」情境 | **平板**（橫向，約 10 吋 / ~1024px 寬） | 桌機/筆電同等視為主要支援對象；手機需堪用但非優化對象 |
| **球友端**（Phase F，未來規劃） | 隨身攜帶、走動中查看的「隨手查一眼」情境 | **手機直式** | — |

第 3.2 節（Mobile-first）與後續各節的排版原則，**僅適用於球友端**；團主控制台的版面設計應以平板橫向寬度為基準校準卡片大小、字級與每列/每排容納數量。

### 3.2 Mobile-first（適用範圍：球友端）

* 主要設計基準為手機直式畫面。
* 保持清楚且穩定的左右邊界。
* 使用一致的內容寬度與水平 Padding。
* 保持適度留白，但避免過度留白。
* 重要操作應容易在單手操作時找到。
* 不使用大型 Dashboard 式多欄 Layout 作為主要手機介面。
* 不應為了填滿畫面而加入沒有產品價值的 UI 元素。

### 3.3 團主控制台的規模基準

* **舒適使用範圍**：1-6 場地／約 20-40 人，版面邏輯需在此區間內不跑版、不出錯。
* **視覺尺寸校準的甜蜜點**：2-3 場地／16-24 人（台灣主流球團規模）——卡片大小、字級、間距應以這個規模「看起來剛剛好」為校準基準，**不是**用 6 場/40 人的極限情境去反推縮小尺寸。
* 6 場以上（大型球團常見用平板/磁鐵板管理的規模）**不在本產品現階段設計範圍內**。
* 實務做法：
  * 球場狀態區：卡片用固定寬度＋自動換行，而非「依場地數動態計算寬度」——2-3 場時維持原尺寸、允許留白；6 場時自然換行成兩排，不需要為撐滿而縮小卡片，也不需要另外設計「多場模式」的特殊版面。
  * 球友名單網格：版面邏輯需支援延伸到 40 人不出錯（例如捲動、換行），但卡片尺寸與字級以 16-24 人的密度校準；40 人情境下需要多滑動一兩次屬於可接受的代價，不應為了消滅這個滑動犧牲甜蜜點規模的體驗。

## 4. Information Hierarchy

每個畫面都必須建立清楚的資訊層級。

建議至少區分：

### Primary Information

使用者完成任務時最需要注意的資訊。

例如：

* 球局日期
* 球局時間
* 場次狀態
* 目前人數
* 目前排點
* 核心操作狀態

### Secondary Information

幫助使用者理解情境，但不是第一眼必須注意的資訊。

例如：

* 場館
* 程度
* 費用
* 場地數
* 備註

### Supporting Information

可以降低視覺權重，但仍必須保持良好可讀性。

不得為了視覺簡潔將重要資訊縮小到難以閱讀。

---

## 5. Card Design

本產品**可以使用 Card**。

Card 應被視為「資訊群組與互動單位」，而不是單純的裝飾。

### 適合使用 Card 的情境

例如：

* 一場獨立的球局
* 一個報到區塊
* 一個排點結果
* 一個獨立的功能入口
* 一個需要點擊進入詳細內容的資訊單位（例如 Phase 2 報到主視圖的每張球友卡片——單張卡片代表一個完整的互動單位：選取／查看狀態／進詳細編輯）

### Card 使用原則

* Card 內資訊應具有清楚的階層。
* 一張 Card 應該代表一個完整的資訊或操作單位。
* 不要將 Card 內的每一個資訊項目再次包裝成小 Card。
* 不要讓所有頁面區塊都變成 Card。
* Card 應以簡潔、輕量為主。

### Card Visual Style

偏好：

* 輕微圓角（見第 6 節，具體數值已收斂定案）
* 乾淨邊界
* 輕量視覺層次
* 必要時使用非常輕微的陰影

避免：

* 超大圓角
* 厚重陰影
* 浮誇的立體感
* 漸層 Card
* Glassmorphism
* 過度裝飾

---

## 6. Border Radius

整體偏好：**輕微圓角、成熟、俐落。**

**具體數值（已定案）**：現有實作使用的 `rounded-2xl`（大圓角）需收斂，改用 `rounded-lg` 或 `rounded-md` 級別，貼近「專業信賴感」的調性；避免所有元件統一使用大圓角造成過度可愛或玩具感。

避免：

* 極端直角造成生硬感
* 超大圓角造成過度可愛或玩具感
* 所有元件都使用相同的大圓角

圓角應該服務於資訊分組與視覺舒適度，而不是成為主要視覺風格。

---

## 7. Shadow

陰影不是主要的視覺語言。

優先使用：

1. Layout
2. Background contrast
3. Border
4. Spacing

建立資訊層次。

必要時可以使用**非常輕微、低存在感的 Shadow**來增加可點擊 Card 或浮動元件的辨識度。

避免：

* 明顯厚重的陰影
* 大範圍模糊陰影
* 透過 Shadow 製造強烈浮空效果

---

## 8. Color Direction（三層色彩系統，已定案）

不再是「品牌色 A/B 二選一」的開放討論，改為明確的三層分工：

### 8.1 中性結構色（主結構）

畫面主結構——背景、卡片、邊框、大部分文字——維持中性灰階（slate 色階），不刻意鋪張顏色。這是畫面的視覺基底，佔比最大。

### 8.2 狀態色（功能性用途，僅限狀態標示）

顏色只保留給「狀態」溝通，且需維持顏色與語意的一致對應，不可挪作他用：

* **綠色**：已完成／成功狀態（已報到、已收費）
* **琥珀／黃色**：待處理／提醒（休息中、待收費、時段將結束）
* **紅色**：需要注意／錯誤（未到、迴避關係）

### 8.3 品牌主色（僅用於主要操作 CTA）

**定案為藍色**，不使用綠色。

原因：綠色已在 8.2 節被用作「已完成」的狀態色；若品牌主色也用綠色，會讓使用者混淆「這顆按鈕是要我按下去，還是在告訴我這件事已經完成了」。藍色可以完整承擔「輕度運動感＋主要操作辨識度」，又不與狀態色系統衝突。

用途範圍嚴格限定：報到、一鍵上場、結算此場等「最重要的下一步操作」，不擴散到其他裝飾性用途。

### Color Principle

* 色彩應該是輕度運動感的來源之一，而不是整個 UI 的裝飾。
* 避免大面積高飽和色彩、大量漸層、多色彩同時競爭。
* 不要為了「運動感」而加入過多視覺元素。
* 整體仍應以中性背景與清楚的文字層級為主。

---

## 9. Primary CTA

Primary CTA 必須具有**非常明確的視覺存在感**，並使用第 8.3 節定案的品牌主色（藍色）。

例如：

* 報到（Phase 2）
* 開始排點 / 一鍵上場（Phase 1）
* 結算此場
* 確認

### CTA 原則

* Primary CTA 與 Secondary Action 必須具有清楚的視覺差異。
* 不要讓主要 CTA 與普通文字連結具有相同視覺權重。
* 不要為了追求極簡而讓主要操作變得難以辨識。
* **Primary CTA 使用品牌主色（藍色），且需與狀態色系統（尤其是「已完成」的綠色）明確區隔，避免辨識混淆。**
* CTA 的尺寸應適合觸控（平板/手機皆需符合，見第 10 節觸控目標），不需要透過巨大尺寸製造存在感。

---

## 10. Interaction Philosophy

使用者應能快速理解：

> **現在在哪裡 → 現在看到什麼 → 下一步可以做什麼**

因此：

* 操作結果需要有清楚的視覺回饋（例如「重算預排」按鈕點擊後短暫顯示「已重新計算」的輕量回饋，這種明確但不誇張的反饋是對的方向）。
* 不應要求使用者猜測哪些元素可以點擊。
* 重要狀態應透過明確的文字、顏色或元件狀態呈現。
* 不要把重要操作隱藏在過多選單或手勢中。
* 互動設計優先考慮現場、快速操作的情境。
* 觸控目標 ≥ 44 × 44px，確保平板/手機皆可正常操作長按與點擊。

---

## 11. Visual Elements to Avoid

請避免以下風格：

* 大量漸層
* Glassmorphism
* 厚重陰影
* 超大圓角
* 過度 Card 化
* 大量插畫
* 過度可愛
* 過度科技感
* AI SaaS 常見的紫色／漸層／玻璃質感視覺
* 大型 Hero Section
* 為了裝飾而增加的圖形
* 資訊過度縮小
* 過度留白導致資訊效率降低
* 看起來像 AI 自動生成的模板網站

---

## 12. Desired Visual Impression

最終 UI 應該接近：

> **專業信賴的管理工具 + 高資訊效率 + 清楚的操作介面 + 輕度運動感**

而不是：

> 運動品牌官網
> AI SaaS Dashboard
> Dribbble 展示頁
> 可愛社群 App
> 高度裝飾性的 Landing Page

---

## 13. Implementation Constraint for Gemini Canvas

在實作 UI 時：

1. 優先遵循本 UI / Visual Specification。
2. PRD 定義功能，本文件定義視覺與排版方向。
3. **先確認正在做的是團主控制台還是球友端**，套用對應的裝置基準（第 3.1 節）——團主控制台以平板橫向寬度校準，球友端才適用 Mobile-first。
4. 團主控制台的卡片尺寸/字級，以 2-3 場／16-24 人的規模校準，同時確保版面邏輯延伸到 6 場／40 人不跑版（第 3.3 節）。
5. 圓角統一使用 `rounded-lg` / `rounded-md` 級別，不使用大圓角（第 6 節）。
6. 色彩嚴格遵循三層分工（第 8 節）：中性結構色為主，狀態色三色僅用於狀態標示，藍色僅用於主要操作 CTA，不混用。
7. 不要自行新增未定義的裝飾性 UI。
8. 不要因為「美觀」而降低資訊辨識度。
9. 不要自行將所有內容 Card 化。
10. 不要自行加入漸層、Glassmorphism、大型插畫或強烈陰影。
11. 不要使用大型 Hero 區域佔據主要畫面。
12. 如果功能需求與視覺效果發生衝突，優先維持功能與資訊辨識度。
13. 如果 PRD 沒有指定視覺細節，請遵循本 Specification，而不是自行套用常見 AI SaaS UI 模板。
14. 優先建立一致、可重複使用的 UI pattern，而不是為每個頁面設計不同風格。

---

## Core Principle

> **這是一個讓羽球使用者快速完成事情的工具，而不是一個展示視覺設計的網站。**

> **讓資訊清楚、讓操作快速、讓重要的事情一眼就看得到；美感建立在這些基礎之上，而不是取代它們。**
