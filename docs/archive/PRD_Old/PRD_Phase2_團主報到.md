# 羽球零打系統 — Phase 2：團主報到 PRD

> 版本：2026/08/24
> 對應範疇：先前六大情境中的 **B（團主辦理報到）**，資料模型已包含 **D（團主開團）** 的最小骨架
> 狀態：設計討論已收斂，尚未實作；本文件為實作前的規格定案

---

## 1. 定位與目標

Phase 2 要解決的不是財務系統，而是團主在活動開始前／報到當下的現場管理問題：

> **確認誰到了 → 確認今天參加條件（方案/時段）→ 確認付款狀態（可選）→ 記錄打球需求（綁定）→ 交給排點系統**

策略選擇：**直接把「活動」這個最小容器一併做出來**，而不是先在現有的全域球員池上硬做報到功能。理由是這份文件的資料模型（方案掛在活動下、活動成員是活動下的子資料）已經天生需要活動容器，晚做只是把現有 ~1800 行程式碼裡所有讀寫 `players` 的地方全部重寫一次；現在做，複雜度是漸進式增加（新增功能），不是打掉重做。

**範圍邊界**：這階段只做「系統裡永遠只有一個進行中活動」的最小版本，不做多活動列表、活動間切換、歷史活動查詢——那些留給後續階段。

## 2. 資料模型

```
Activity（活動，MVP 階段全系統僅一筆）
├── id, name
├── startTime                        // 活動開始時間，絕對時間
├── financeEnabled: boolean           // 是否啟用帳務記錄（總開關）
├── autoStatusEnabled: boolean        // 是否依方案時間自動判斷 未開始/時間到
├── enabledPaymentMethods: string[]   // 例如 ['cash','coupon','transfer']（活動層級設定）
├── defaultPaymentMethod: string|null // 可選；為 null 代表不預設，報到允許空值
├── plans: Plan[]
└── members: ActivityMember[]

Plan（方案）
├── id, name                          // 例如 "A方案"
├── startTime, endTime                // 絕對時間，團主自行維護，延遲開場需自行調整
├── amount                            // 應付金額
└── matchEligible: boolean            // 排點資格（目前預設 true，保留欄位彈性）

ActivityMember（活動成員 —— 報到與排點共用同一份資料）
├── id
├── playerRefId                       // 關聯到球友的原始/跨場資料（若有）
├── displayName                       // 本場活動顯示名稱（可現場編輯，不影響原始球友資料）
├── gender, level
├── planId                            // 所屬方案
├── customTime, customAmount          // 僅在「自訂例外」時才寫入，預設為空、直接讀 plan 的值
├── checkinStatus: 'notArrived' | 'checkedIn'
├── attendanceState: 'idle' | 'playing' | 'rest' | 'notStarted' | 'timeUp'
│     // notStarted = 方案時段尚未開始；timeUp = 方案時段已結束
│     // 這兩個新狀態不進入排點候選池，但在 UI 上與「休息」明確區分
├── noShowStatus: null | 'pendingCharge' | 'charged' | 'waived' | 'cancelled'
│     // 僅在 checkinStatus === 'notArrived' 時有意義
├── paymentStatus: 'unpaid' | 'paid'
├── paymentMethod: string | null      // 允許空值（未紀錄）
├── note: string                      // 非結構化備註，與上述狀態欄位分離
├── matchesCount, waitCount           // 沿用現有排點欄位
├── persistentBinds: string[]         // 沿用現有「兩兩綁定」，適用 2-4 人小組
├── bindGroupId: string | null        // 新增：多人（5人以上）綁定群組，見第 7 節
├── tempBind1Match, tempOppose1Match, avoidList
│     // 沿用現有排點欄位，不受本次改動影響
```

**與現有排點 demo 的整合點**：現有 `players` 陣列的欄位（checkedIn/status/matchesCount/waitCount/persistentBinds/...）直接併入 `ActivityMember`，排點演算法讀 `activity.members` 取代原本讀 `players`，邏輯本身不需要重寫，只是資料來源換一層。

## 3. 方案與時段

- 方案時間為**絕對時間**（例如 09:00–11:00），非相對於活動開始時間的偏移量——團主自行維護，延遲開場時自行手動調整對應方案的時間，系統不做自動平移。
- `autoStatusEnabled` 開啟時：系統依「現在時間」對比每位成員所屬方案的 startTime/endTime，自動將 `attendanceState` 在 `notStarted` / `idle` / `timeUp` 之間切換（不影響 `playing`/`rest`）。
- 關閉時：系統不自動變更狀態，團主可用批次操作（依方案篩選、一鍵設定狀態）手動處理整批人。
- **方案時間到，不強制中斷進行中的比賽**：
  - 若該成員此刻不在場上：時間一到直接標記為 `timeUp`，退出候選池。
  - 若該成員正在場上：畫面標記「這場結束後即時間到」，實際狀態轉換發生在**該場結算的當下**，避免打斷球局。
- 只支援預設方案（不開放個別自訂時間/金額）為主流程；`customTime`/`customAmount` 欄位保留給未來的例外處理，Phase 2 暫不開放 UI 入口。

## 4. 報到主視圖：緊湊網格 + 底部工具列

### 4.1 卡片（網格式，不因人數多寡切換版型）

- 固定小尺寸卡片，鋪滿畫面，30-40 人可一次掃視完畢
- 卡片上只放最關鍵即時資訊：**姓名、級數、報到狀態、方案標籤、綁定色條/迴紋針圖示**
- 不在卡片上放付款方式、備註等次要屬性的常駐按鈕（避免卡片被撐大、資訊密度下降）

### 4.2 互動流程

**單點卡片 = 選取（可複選，反白呈現），不直接觸發任何動作**——選取本身無副作用，不管誤觸幾次都可以再點一次取消，安全。

**選取 ≥1 人**：畫面底部浮出固定工具列：
- 「已選 N 人」提示
- 「報到」按鈕（固定位置，右下角或整條置底最右側，大拇指熱區）
- 「付款方式」選擇器（點了才展開選單；不點＝空值，或套用活動設定的預設付款方式）

**選取 ≥2 人**：工具列額外出現「綁定」按鈕——一次把整批選取的人互相建立綁定關係（不限定剛好 2 人，3 人以上朋友揪團一次處理）。

**操作路徑範例**：
- 最短路徑（單人報到，最常見）：選人 → 報到，2 次點擊
- 含付款：選人 → 付款方式 → 報到
- 含綁定：選 3-4 人 → 綁定 → 報到
- 各動作互相獨立、順序自由，付款與綁定皆可略過

**長按/點擊單一人（非批次）**：進入該人的詳細編輯面板（彈窗或 bottom sheet），可修改：顯示名稱、方案、金額（自訂例外）、付款狀態、備註、查看目前綁定關係列表。

### 4.3 頁籤 / 篩選 / 排序 / 搜尋

- **頁籤**（主要工作情境切換，顯示人數）：全部｜未報到｜已報到
- **篩選**（縮小範圍）：性別｜級數｜方案｜時段｜付款狀態｜**是否綁定**
- **排序**：預設為報名／接龍順序；可切換姓名、級數
- **搜尋**：快速找到特定的人

## 5. 稽核視圖（次要，條列式）

定位：**不是即時報到現場用的視圖，是活動結束後或需要仔細核對帳務時用的視圖**。

- 表格式呈現，每列涵蓋較完整資訊（姓名/級數/方案/報到/付款方式/付款狀態/未到處理/備註）
- 偏**唯讀展示**（純文字/標籤），不在每列常駐一排操作按鈕
- 需要修改時，點擊該欄位彈出小型下拉選單/彈窗進行編輯（例如點付款狀態文字，彈出「現金／LINE Pay／轉帳／未付」選項）
- 這樣可避免像早期 prototype 那樣，因為每列塞太多常駐按鈕，導致找人需要多次下滑

---

## 6. 付款與帳務

- **總開關**：活動設定「啟用帳務記錄」（`financeEnabled`）。關閉時，所有付款相關 UI（付款方式選擇器、付款狀態、帳務摘要）整個不出現，名單卡片與工具列只剩報到相關功能，介面更輕量。
- **啟用時**：
  - 活動層級勾選本場接受的付款方式（現金/球券/轉帳/LINE Pay 等），報到頁只顯示勾選過的選項
  - **報到與付款完全解耦，允許空值報到**——付款方式沒選也能完成報到，避免報到動作被付款選擇卡住
  - 可選：活動層級設定「預設付款方式」，開啟後，報到工具列的付款選擇器預先帶入該值，多數情況（例如九成人付現金）可以更快完成；未開啟則維持空值
  - 「先報到後付款」的情境（待付款）**Phase 2 暫不處理**——沒有這條路徑，付款狀態欄位仍保留，但 UI 不主動開放
  - 帳務摘要（活動當日層級，非完整財務系統）：
    - 出勤：報名 N 人／已報到 N 人／未到 N 人
    - 金額：應收／已收／待收
    - 各付款方式金額分布
    - 額外顯示「未記錄付款方式：X 人」，提醒團主事後補（透過稽核視圖點擊補上，不需重新走報到流程）

## 7. 綁定機制

分成兩種資料結構，服務不同規模的需求：

### 7.1 兩兩綁定（沿用現有 `persistentBinds`）

- 適用 2-4 人的小組，資料結構與排點演算法的評分邏輯**維持現有實作不變**（每人存一份「跟誰綁定」的清單，命中 +50、缺席 -100）
- 剛好 4 人互綁時運作正常（每人的 3 個綁定對象都能同時進場）

### 7.2 綁定群組（新增 `bindGroupId`，適用 5 人以上）

**問題**：一場比賽固定 4 人，5 人以上互綁時，用兩兩綁定的評分邏輯（缺席即 -100，無但書）會導致這個群組結構性地不可能被完整滿足——任何候選組合都會有至少 1 人缺席，累積懲罰極重，系統反而會盡量避開這整組人，效果與期望完全相反（不是程式錯誤，是評分模型不適用於 >4 人的場景）。

**解法**：
- 新增 `bindGroups`：`{groupId, memberIds: [...]}`，取代個人身上存 pairwise 陣列的方式
- 評分邏輯改為：候選 4 人組合中，屬於同一個 `bindGroupId` 的人數越多，分數越高（4 人全同組給最高分、3 人給中等分⋯），**完全不因「同組其他人這場沒被排到」而扣分**——這才符合「一次只能上 4 個、其他人排隊等下一輪」的物理限制
- 沒被排到的成員，靠既有的等候優先（W1，等候次數加權）機制自然被排進下一輪，不需要額外的懲罰機制去「催促」系統湊齊全組

### 7.3 UI

- 卡片上：迴紋針圖示 + 色條表示有綁定關係（同組同色）；點擊不跳提示，完整綁定資訊放進該人的詳細編輯面板
- 篩選新增「已綁定」

## 8. 未到處理

- 四種狀態（僅在 `checkinStatus === 'notArrived'` 時有意義）：**待收費／已收費／不予追究／已取消**，明確區分「取消」≠「單純沒到」
- 可在**活動進行中隨時處理**，不強制等活動結束才能操作——現場常有人臨時說不來，團主應該能當下順手標記
- 備註為獨立、非結構化欄位，不可拿來替代上述結構化狀態（避免後續無法統計）

---

## 9. 成員管理與匯入

- 成員的新增／匯入／編輯提升到**活動層級**（「活動成員管理」），報到頁與排點頁都讀同一份資料，不再各自維護
- 報到頁仍可提供「＋臨時新增」的快速入口，但寫入的是同一份 `activity.members`
- 匯入解析需一併強化兩個既有痛點（可與 Phase 2 開發一起處理，不必等它單獨排期）：
  - 接龍格式常見的行首編號前綴（`1.姓名/6`）需先剝除再解析
  - 全形符號（／，．等）需與半形符號一併支援，避免中文輸入法自動轉換全形導致整行解析失敗

---

## 10. 顯示名稱

- `ActivityMember.displayName`（本場活動顯示名稱）與球友原始資料分離，現場可自由編輯，解決報名名單同名混淆的問題，不會永久修改球友的原始資料

## 11. 明確排除（Phase 2 不做）

- 多活動管理（活動列表、切換、歷史查詢）
- 先報到後付款（待付款）流程
- 自訂方案（個別修改時間/金額）的正式 UI 入口——欄位保留，入口暫不開放
- 完整財務系統（月營收、利潤、團主間分帳、複雜圖表）
- 時間到強制中斷比賽／直接請人下場

## 12. 尚待驗證（實作後透過 Demo/Prototype 確認）

1. 底部工具列在「已選多人 + 部分人適用不同方案」時，付款方式/綁定操作的具體互動細節（例如金額加總顯示方式）
2. 稽核視圖的欄位編輯彈窗，在觸控裝置上的實際操作手感
3. `bindGroups`（5 人以上）與既有 `persistentBinds`（2-4 人）兩套機制並存時，UI 上如何讓團主清楚分辨「這是小組綁定還是兩兩綁定」，避免混淆
4. `autoStatusEnabled` 關閉、改用批次手動調整時，團主實際操作頻率是否如預期般低（如果太頻繁，可能要重新考慮方案 1 的自動平移機制）

## 13. 與現有排點系統（Phase 1 Demo）的關係

- 排點演算法（`evaluateMatchupScore`）需要修改的部分：候選池從 `players.filter(...)` 改讀 `activity.members`；新增第 7.2 節的群組綁定評分；`attendanceState` 新增的 `notStarted`/`timeUp` 需排除在候選池之外（等同現行 `idle` 過濾條件的擴充）
- 排點演算法其餘邏輯（W1-W4、tempBind1Match、tempOppose1Match、avoidList、場地部署與結算）**不受本次改動影響**，可直接沿用
