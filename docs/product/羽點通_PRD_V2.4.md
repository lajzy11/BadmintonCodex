## 2. 產品定位、目標與範圍

### 2.1 產品定位

本產品是以羽球零打團主為第一優先使用者的現場營運控制台。第一版核心不是公開報名平台，而是協助團主完成：

- 建立活動、方案與場地。
- 匯入及管理活動名單。
- 現場快速報到與收款登記。
- 依等待、場數、級數、重複配對與人際關係進行智慧排點。
- 管理有順序的多組預排與球場。
- 結算、語音叫號及對戰紀錄。
- 查看活動出勤與帳務摘要。

### 2.2 核心產品目標

1. 降低團主同時處理名單、收款、排點與叫人的認知負荷。
2. 提升等待時間、已打場數與對戰強度的公平性。
3. 讓現場高頻操作能以平板或桌機快速完成。
4. 讓手機操作不依賴拖曳，仍能完成報到與排點。
5. 建立可延伸至球團組織、球友帳號與公開報名的資料結構。

### 2.3 第一版角色

- **球團擁有者／團主（Owner）**：建立球團與活動，管理所有活動資料。
- **無帳號球友（Demo 自助報到者）**：透過活動 QR Code 認領名單並完成 Demo 付款報到。

第一版介面不開放多位管理員或一般球團成員帳號，但資料模型需保留未來多人角色擴充能力。

### 2.4 產品層級

產品資訊架構分為四層：

1. **系統層**：品牌、公開活動探索與跨球團的球友功能。
2. **帳號層**：登入身分、個人資料、偏好與安全設定。
3. **球團層**：球團首頁、球團設定與其活動集合。
4. **活動層**：單一活動的總覽、名單與報到、排點作業。

「球團首頁」是目前所選球團的管理入口，不是整個系統首頁或帳號首頁。未來球友前台上線後，系統層可另有「探索活動／我的報名」首頁，兩者不可混為同一頁。

## 3. 帳號、球團與雲端資料

### 3.1 技術方向

第一版採用具備 Authentication、PostgreSQL、Row Level Security 與即時同步能力的雲端後端（建議 Supabase）。

- 雲端資料庫是主要資料來源。
- LocalStorage 僅保存主題、上次使用的排序／檢視模式及必要的短期離線快取。
- 密碼交由正式驗證服務處理，不以明文存入一般資料表。
- 帳號名稱登入需要安全的伺服器端對應層，不能把帳號對應資料公開給前端查詢。

### 3.2 帳號名稱

- 4–20 個字元。
- 僅允許英文字母、數字、底線。
- 必須至少包含一個英文字母或數字，不能全部是底線。
- 不分大小寫，儲存與查詢時統一轉為小寫。
- 全系統不可重複。
- 第一版建立後不可修改。

### 3.3 密碼

- 8–64 個字元。
- 至少包含一個英文字母與一個數字。
- 允許常見特殊符號。

### 3.4 第一版註冊欄位與開團流程

- 暱稱：2–20 個字元，僅允許中文、英文字母與數字。
- 帳號：遵循 3.2 帳號名稱規則。
- 密碼：遵循 3.3 密碼規則。

第一版唯一入口為「註冊並建立球團」。註冊成功後以「%暱稱%的球團」作為初始球團名稱，建立 Auth User、Profile、Organization 與 Owner Membership，並直接登入球團管理介面；團主可於球團設定修改球團名稱。

這是第一版的產品入口，不是「每個帳號永久都必須擁有一個球團」的資料規則。實作需拆分為可重用的帳號建立、Profile 建立、球團建立與 Membership 建立服務；資料庫內的 Profile、Organization 與 Membership 寫入應以交易或具備清理、重試及冪等能力的流程確保一致性。

### 3.5 登入

- 帳號。
- 密碼。
- 保持登入。
- 錯誤訊息統一為「帳號或密碼不正確」，不揭露帳號是否存在。
- 登入頁提供「以訪客身分體驗」入口。訪客展示模式使用瀏覽器工作階段隔離的固定示範資料，不建立 Auth User、不讀寫正式球團資料，並在側欄帳號區明確標示「訪客展示模式」。
- 訪客可瀏覽球團首頁、活動概況、名單與排點畫面；離開訪客模式或結束瀏覽器工作階段後清除訪客身分。

### 3.6 第一版帳號功能

可使用：

- 查看目前帳號。
- 修改團主顯示名稱。
- 一般登出。

保留但停用，並標記「上線版」：

- 修改密碼。
- 忘記／重設密碼。
- 登出其他裝置。
- 匯出我的資料。
- 刪除帳號。

第一版因沒有 Email、手機或其他可驗證身分，無法自行找回密碼；註冊與登入頁需明確提醒使用者保存帳號密碼。

### 3.7 首次使用引導

登入後若尚未完成球團基本資料：

1. 確認球團名稱。
2. 選填預設聯絡資訊與常用用球。
3. 選擇建立第一個活動、先新增常用球館或稍後設定。

選擇稍後設定時，直接進入空白球團首頁。

### 3.8 帳號與身分架構原則

- 帳號是跨球友前台與團主管理後台共用的登入身分容器，不區分「買家帳號」與「賣家帳號」。
- `UserProfile` 不保存單一 `organizationId`、`isOrganizer` 或永久固定角色。
- 球團身分由 `OrganizationMembership` 關聯決定；同一帳號未來可同時是 X 團團主、Y 團一般成員，或不屬於任何球團。
- 活動報名不等同加入球團。球友可報名 Z 團活動而不成為 Z 團成員。
- 未來活動名單可透過 nullable 的 `linkedAccountId` 連結帳號；人工新增或匯入且尚未認領的成員仍可沒有帳號關聯。
- 查詢「目前帳號所屬球團」必須透過 Membership 回傳清單，不得從 Profile 讀取或在全域狀態永久假設單一 `organizationId`。
- 第一版畫面可因目前入口限制而只處理一個球團，但底層介面需保留零個、一個與多個球團的結果。

### 3.9 未來前台與管理後台分流

- 所有登入帳號皆可使用球友功能，例如探索活動、我的報名與球友資料。
- 只有在球團具有 owner／admin Membership 的帳號，才顯示球團與活動管理入口。
- 未來一般註冊只需建立 Auth User 與 Profile；使用者主動「建立球團」時才建立 Organization 與 Owner Membership。
- 登入後優先返回原始 `returnTo`；沒有指定時回到最近使用情境。未來首次登入的一般帳號預設進入球友首頁，而非強制開團。

## 4. 活動狀態與球團首頁

### 4.1 活動狀態

#### 草稿 `draft`

- 尚未完成三步建立流程。
- 不因時間到達而自動開始。
- 不可使用報到、QR Code、排點及付款。
- 計入未封存活動上限。
- 可繼續編輯或刪除。

#### 即將開始 `scheduled`

- 已完成活動建立。
- 現在時間早於最早方案開始時間。
- 可整理名單、提前開啟自助報到及完成 Demo LINE Pay 付款。
- 到達最早方案開始時間後自動成為進行中。

#### 進行中 `in_progress`

- 現在時間已達最早方案開始時間，無需團主手動開始。
- 報到、排點、自動模式及對戰功能正常運作。
- 超過最晚方案結束時間後仍維持進行中，直到團主手動結束。
- 超時後顯示「已超時，尚未結束」。

#### 已結束 `ended`

- 必須由團主手動結束。
- 關閉自助報到與自動模式。
- 不可新增預排或開始新比賽。
- 可修正帳務、補登比分、查閱與匯出。
- 計入未封存活動上限。
- 可重新開啟或封存。

#### 已封存 `archived`

- 不計入未封存活動上限。
- 預設唯讀。
- 可查看與匯出。
- 可解除封存；解除後不得超過活動上限。

### 4.2 自動開始判斷

活動正式開始時間為所有方案中最早的完整 DateTime。系統可於讀取活動或第一次操作時，依目前時間推導並同步狀態，不要求背景頁面持續開啟。

若團主在活動開始時間已過後才完成建立，需提示建立後會直接進入進行中，但不阻止建立。

### 4.3 手動結束

結束前檢查：

- 有比賽進行中：禁止結束，必須先結算或取消。
- 有預排：要求先清空，可由系統一次清空。
- 有待確認付款或帳務：警告但允許結束。
- 有尚未報到者：警告但允許結束。

### 4.4 活動上限

每個球團最多同時存在 5 個未封存活動。

計入：草稿、即將開始、進行中、已結束未封存。

達到上限時停用建立與複製活動，提供前往封存或刪除草稿的入口。

### 4.5 球團首頁定位與區塊

原「活動中心」正式更名為「球團首頁」。此頁負責呈現目前所選球團的活動入口與近期營運狀態，不承擔單一活動的詳細管理，也不作為跨球團的系統首頁。

頁面由上而下固定稱為「頁面功能列、Banner 區塊、範本區塊、活動區塊」。頁面功能列標題為「球團首頁」且不放 CTA；Banner 緊接功能列，顯示球團名稱、簡介、使用量，並在標題列右側提供唯一主要 CTA「建立活動」。頁面功能列標題、Banner 內容、範本與活動列表需共用主內容左側基準線；Banner 只讓背景滿版，不另外置中內容。

Banner 內以全寬、無左側直線的「活動使用量」區塊常駐顯示未封存活動使用量：0–4 筆時顯示尚可建立的活動數，5 筆時切換為黃色警示並提供查看可封存活動的入口，不另建立 Banner 外的使用量警示區塊。存在活動範本時，在 Banner 與活動區塊之間顯示可直接套用的範本區塊；沒有範本時不保留空白區塊。範本採緊湊寬度，範本按鈕內不顯示重複操作文案，並在所有範本之後以不同樣式固定顯示獨立的「建立副本」按鈕。

活動區塊的狀態頁籤為：

- 進行中。
- 即將開始。
- 草稿。
- 已結束。
- 已封存。

活動區塊標題為「活動列表」。所有底線式頁籤不使用底色，點擊區域彼此相接且具有足夠寬度，選取項目只以藍色底線辨識；此規則同樣適用其他頁面的底線式頁籤。

「進行中」狀態使用黃色左側線條與黃色標籤，比「即將開始」具備更強的即時辨識。狀態色左側線條只與兩行文字內容同高，不延伸至整列。活動資料列的主要資訊固定為上下兩行：第一行「日期、活動名稱（有值時）、狀態」，第二行「時間、球館、初始場地數」；活動主要操作與 More 選單之間保留足夠點擊間距，避免誤觸。

多個活動時間重疊時只警告，不硬性禁止。若同時有多個進行中活動，登入後停留在球團首頁，由團主自行選擇。

## 5. 三步活動建立流程

### 5.1 共通規則

- 可儲存草稿。
- 草稿不完整時可離開並稍後繼續。
- 只有完成全部必填與驗證後才能正式建立活動。
- 從範本建立時，活動日期預設今天。
- 活動日期不可早於今天。

### 5.2 步驟一：活動基本資料

#### 球團

- 第一版自動帶入目前唯一球團，唯讀。
- 修改球團名稱需前往球團設定。

#### 活動日期

- 必填。
- 不可選擇過去日期。
- 從範本建立時預設今天。

#### 球館

第一版不提供內建球館搜尋，只提供：

- 從「我的球館」選擇。
- 新增球館。

新增球館必填：

- 球館名稱。
- 縣市。
- 行政區（依縣市連動）。

非必填：

- 地址。
- 地板材質。
- 備註。

「儲存到我的球館」預設開啟。活動保存球館快照；私人球館日後修改不回寫既有活動。

#### 初始場地數

- 必填，正整數，1–20。
- 預設 1。
- 只代表活動進入排點頁時建立的球場卡數量。
- 活動期間由團主在排點頁手動增減，不提供時段場地配置與自動增減。

#### 招收人數

提供兩個明確選項：

- 不限制。
- 限制人數。

選擇限制時：

- 需填 1–100。
- 建議值為初始場地數 × 8。
- 可自行修改。
- 第一版尚未開放公開報名，因此只作提醒；團主手動新增或匯入超過上限時警告但仍可確認加入。
- 活動已有成員時，不得把上限調低至有效名單人數以下。

#### 級數範圍

- 必填，1–18。
- 最低不得大於最高。
- 範圍外球友可加入，但新增或匯入時警告團主。

#### 上場方式

- 系統排點（預設）。
- 人工排點。
- 自由上場。

使用三張說明卡，不使用下拉選單。活動建立後可切換，但切換至自由上場前需處理既有預排。

#### 更多活動資訊（全部非必填）

- 活動自訂標題。
- 指定用球。
- 團主聯絡資訊。
- 簡介／注意事項。

### 5.3 步驟二：方案與帳務

#### 參與方案

- 至少 1 個，最多 5 個。
- 系統依序產生 A–E，不可自訂代號。
- 新增方案時使用 A–E 中尚未被使用的最前方代號；刪除方案不會重新命名仍存在的其他方案。
- 每個方案必填開始與結束時間。
- 不提供「具備排點資格」開關；第一版所有方案皆可參與排點。
- 活動整體時間由最早方案開始與最晚方案結束自動推導。

#### 跨午夜

支援跨午夜，例如 23:00–01:00。若結束時間早於開始時間，解讀為隔日並顯示「隔日」。資料庫儲存完整 DateTime。

#### 新增與刪除方案

- 至少保留一個。
- 刪除中間方案後不重新編號其他方案。
- 無成員時可直接刪除。
- 已有成員時不可直接刪除，必須選擇一個其他方案，把全部成員統一移入後才能刪除。
- 移動前顯示時間與金額差異。

#### 依方案時間自動判斷排點資格

- 預設開啟。
- 未開始：不進入候選池。
- 有效時間內：可排點。
- 已超時：不再進入候選池。
- 到期時正在比賽：允許完成，結算後失去資格。

#### 帳務與付款記錄

- 預設開啟。
- 關閉時隱藏所有付款、金額與 LINE Pay 自助付款功能。
- 開啟時每個方案金額必填，0–10,000 元整數。
- 0 代表免費方案。
- 第一版不提供單一球友例外金額或例外時間。

#### 付款方式

- 現金。
- LINE Pay。
- 轉帳。
- 球券。
- 其他。

帳務開啟時至少選一種。預設付款方式屬於活動層級，不屬於個別方案。

球券只記付款方式與方案帳面金額，不記張數。

#### LINE Pay 自助付款 Demo

- 選項固定顯示。
- 未完成球團 LINE Pay Demo 設定時停用，說明需至「球團設定 → 付款與串接」開啟。
- 未啟用帳務或活動未選 LINE Pay 時停用。
- 不產生真實交易。

### 5.4 步驟三：確認與建立

呈現：

- 活動基本摘要。
- 方案與帳務摘要。
- 系統檢查結果。
- 可展開的進階排點設定。
- 主動勾選的「同時儲存為活動範本」。

#### 阻擋建立的錯誤

- 日期、球館或場地數缺漏。
- 球館缺少縣市或行政區。
- 級數範圍錯誤。
- 沒有方案或方案時間缺漏。
- 啟用帳務但方案金額缺漏。
- 啟用帳務但未選付款方式。
- 選擇限制人數但數字無效。

#### 僅提醒

- 招收人數不限制。
- 平均每面超過 8 人。
- 沒有聯絡資訊。
- 使用 LINE Pay 付款方式但尚未開啟 Demo。
- 所有方案免費。
- 方案時段彼此完全沒有重疊。

### 5.5 進階排點設定

只有系統排點模式顯示，不暴露 W1、W2 等技術數值。

#### 排點優先原則

- 均衡公平（預設）：等待與已打場數並重，等待過久者仍有最高優先。
- 等待優先。
- 場數優先。

#### 實力接近程度

- 寬鬆。
- 均衡（預設）。
- 嚴格。

皆為軟性權重，不是絕對級差限制。

#### 避免重複同場

- 不特別避免。
- 適度避免（預設）。
- 強烈避免。

重複統計需區分相同搭檔、相同對手與完全相同四人。

#### 雙打組合偏好

- 不限（預設）。
- 優先混雙。
- 優先男雙／女雙分開。

皆為軟性偏好，第一版不提供強制混雙。

#### 語音叫號

- 預設啟用。
- 重複 1–3 次，預設 2。
- 語速 0.5–1.5，預設 1.0。
- 提供測試語音。

### 5.6 建立後名單空狀態

- 匯入報名名單。
- 新增第一位球友。
- 稍後再加入成員。

選擇稍後加入後正常進入活動總覽，不反覆彈窗。

`活動總覽｜名單與報到｜排點作業`

活動識別不可在每個頁籤重複佔據大面積；頁籤以下應直接呈現該工作區內容。分享、編輯、結束等低頻功能收在活動操作入口。

## 7. 活動概況總覽

### 7.1 頁面定位

總覽回答：活動是什麼、來了多少人、錢收得如何、是否有需要處理的事情。總覽不提供完整名單編輯、批次報到、排點與完整對戰紀錄。

### 7.2 活動識別

顯示：

- 球團與活動自訂標題。
- 日期與整體時間。
- 球館、縣市、行政區。
- 初始場地數。
- 上場方式。

主要快捷：符合條件時開啟自助報到、分享活動。名單匯入與新增球友集中於「名單與報到」頁，不在概況頁重複提供。

次要操作：編輯活動、存為範本、結束活動。「存為活動範本」置於儀表板底部的活動管理列，避免與現場高頻操作競爭。

自助報到是現場入口，符合顯示條件時置於 Banner 後、儀表板前的醒目操作區；不得埋在統計區塊之後。

### 7.3 報到摘要

- 活動有效名單人數。
- 已報到。
- 尚未報到。
- 有設定限制時顯示目前人數／上限與剩餘名額。

點擊摘要前往已套用對應篩選的名單頁。

不顯示休息、時間未到、上場中或已進行對戰數。

概況頁以三個主要儀表板模組呈現：「報名與出席」「帳務與付款方式」「方案與各時段人數」。可使用單層資訊卡、圓環圖、進度條與水平長條圖強化辨識，但不得巢狀堆疊多層卡片。

### 7.4 帳務摘要

帳務開啟時顯示：

- 應收金額。
- 已收金額。
- 待收金額與待收人數。
- 各付款方式已確認金額。

Demo LINE Pay 金額需明確標示 Demo。

應收排除已取消與不予追究者。球券以方案帳面金額統計，不顯示張數。

### 7.5 方案與時段統計

每個方案顯示時間、金額、名單人數、已報到人數與已收金額。帳務關閉時隱藏金額資料。

方案設定摘要不得另設重複區塊；方案的時間、金額與人數統一在此模組呈現。

### 7.6 各時段有效人數

- 兩個以上方案時才顯示；只有一個方案時隱藏。
- 依方案重疊自動計算每 30 分鐘有效人數。
- 相鄰區間人數相同時可視覺合併。
- 不換算場地負載，不使用初始場地數推測全時段租場。

### 7.7 待處理事項

只顯示需要團主行動的異常。

- 尚未付款與尚未報到不得在球友所屬方案開始前顯示。
- 方案開始後仍未報到或付款才提示。
- 球館地址非必填，不提醒。
- 不顯示理論上會被開啟前驗證阻止的不可能狀態。

### 7.8 已取消球友

- 不計入有效名單與招收人數。
- 不進入報到、排點與應收。
- 一般總覽不顯示為 KPI。
- 保留於名單已取消狀態與完整封存資料。

## 8. 名單與報到

- 已報到。

- 新增一位。
- 批次貼上名單。

- 搜尋。

必填：顯示名稱、級數、方案。性別與備註非必填。

### 8.11 匯入名單

流程：輸入／選檔 → 解析預覽 → 確認匯入。

預覽顯示：成功、需確認、無法匯入、疑似重名、級數超出範圍、無效方案、超過招收提醒。

匯入預覽提供「全部／需確認／無法匯入」快速篩選，修正資料後即時重新判斷分類。深色介面中的警示與錯誤列不得使用大面積黃底或紅底，改用左側語意色線條及高對比文字；視窗內容與固定操作列皆維持深色底。

若名單只有可略過的提醒，按下匯入後須以 Alert 對話框列出匯入總人數、級數超出活動範圍人數、疑似重名人數及匯入後超過招收上限的結果，提供「返回檢查」與「仍要匯入 N 人」。具有阻擋錯誤的名單不得進入確認 Alert。

匯入預覽在手機／窄螢幕改為逐筆直向編輯卡，不保留需要橫向捲動的桌機表格；每個控制須顯示欄位名稱。篩選列使用等寬三欄，底部操作列維持可見，確認 Alert 改為單欄操作。

解析規格：

- 支援 CSV 與純文字。
- 支援半形／全形斜線、反斜線、逗號、頓號與 Tab。
- 先辨識性別 M／F／男／女，再辨識方案代號。

- 數字辨識為級數。
- 無法辨識的文字歸入備註。
- 剝除常見接龍行首編號。
- 單筆錯誤不阻斷整批，允許在預覽修正。

第一版不提供整批復原匯入。

### 8.12 取消報名

- 取消不是永久刪除。
- 從有效名單、招收、報到、排點與應收排除。
- 保留於已取消篩選。
- 可恢復；恢復時重新檢查人數與級數提醒。
- 已有對戰紀錄者不可永久刪除。

## 9. 自助報到與 LINE Pay Demo

### 9.1 開啟條件

- 帳務開啟。
- 活動付款方式包含 LINE Pay。
- 球團已啟用 LINE Pay Demo。
- 活動已有可認領成員。
- 活動尚未結束。

不符合時不顯示入口。即將開始階段可由團主提前手動開啟，並允許球友完成 Demo 付款。

### 9.2 QR Code

- 使用可撤銷的活動報到 Token。
- 不直接暴露資料庫 ID 或名單資料。
- 關閉自助報到後 Token 失效；重新開啟產生新 Token。

### 9.3 球友端流程

1. 掃描活動 QR Code。
2. 確認活動名稱、日期、時間與 Demo 說明。
3. 直接顯示尚可認領的完整名單，支援姓名搜尋與方案篩選。
4. 選擇姓名。
5. 確認姓名、級數、方案、時間與金額。
6. 點擊 LINE Pay Demo 付款。
7. 顯示模擬建立訂單、跳轉、處理中與付款成功。
8. 顯示報到成功。

第一版不做身分驗證、四位數認領碼或 LINE Login。畫面需說明為 Demo 自助認領。

### 9.4 認領規則

- 已認領與已取消者不出現在可認領名單。
- 同一身分只能認領一次。
- 同時競爭時，以資料庫第一筆成功寫入者為準，另一端顯示已被認領。
- 團主可從詳細面板解除錯誤認領。
- 球友不能自行修改姓名、級數、方案或金額。

### 9.5 Demo 付款紀錄

- `provider = line_pay`。
- `environment = demo`。
- `status = paid`。
- 產生 `DEMO-...` 交易編號。
- 所有頁面明確標示不會扣款。

提前報到後，球友為已報到／已付款，但在方案開始前不進入排點候選池。

## 10. 智慧排點與現場球場管理

### 10.1 第一版操作原則

- 完全不實作拖曳。
- 所有裝置使用點擊選取＋情境工具列。
- 長按保留作為查看球友詳情，不與拖曳競爭。

### 10.2 排點候選資格

球友同時符合以下條件才可自動排點：

- 已報到。
- 在場狀態為等待 `idle`。
- 目前位於方案有效時間內，或取得特定預排的一次性超時許可。
- 不在球場中。
- 不在其他預排中。
- 未取消。

### 10.3 時間衍生狀態

- 尚未開始。
- 目前有效。
- 時間已到。

此狀態依目前時間與方案即時計算，不作為可被人工任意修改的 attendanceState。

### 10.4 排點引擎

綜合考慮：

- 等待輪數。
- 已打場數。
- 隊伍平均級差，採平方衰減。
- 相同搭檔、相同對手與相同四人。
- 綁定與單場指定關係。
- 避免同場。
- 雙打組合偏好。

運算需放入 Web Worker，避免主執行緒凍結。常規 20–40 人需設定逾時保護；逾時時提供可理解的降級結果或提示。

### 10.5 關係規則

第一版支援：

- 兩人長期同隊綁定。
- 僅綁一場。
- 對戰一場。
- 避免同場。

不支援 5 人以上群組綁定。

指定四人對打可用 AB、CD 分別綁定，再設定 AC 對戰。

規則優先順序：

`避免同場 ＞ 指定對戰一場 ＞ 僅綁一場 ＞ 長期綁定 ＞ 一般排點權重`

衝突時明確提示並禁止建立無法同時成立的關係。關係需雙向生效並在刪除／取消時清除殘留引用。

### 10.6 頂部控制列

- 目前上場方式。
- 自動模式開關（只在系統排點顯示）。
- 智慧排點。
- 新增球場。
- 新增預排。
- 對戰紀錄。
- 排點設定。

自動模式不屬於活動建立設定，只能在排點頁即時切換。

### 10.7 球場與預排版面

同一主要工作區內分為兩個有標題序列：

1. 球場。
2. 接下來上場。

兩種卡片尺寸與內部四人結構一致，但以標題與顏色清楚區隔。

### 10.8 球場管理

- 初始球場數來自活動設定。
- 活動中可手動新增／刪除。
- 至少保留一面。
- 比賽中不可刪除。
- 可重新命名，歷史紀錄保留當時名稱快照。

球場卡片顯示：名稱、狀態、計時器、四人、隊伍、結算。

語音叫號以小型外層按鈕顯示於卡片標題列，不收進更多選單；視覺可小但觸控範圍至少 44 × 44px。空場時停用。

更多選單：編輯名稱、調整場上成員、查看本場、取消本場、刪除空場。

### 10.9 多預排

- 預設 1 組。
- 排點頁可增減。
- 有明確順序：預排 1（下一組）、預排 2、預排 3……
- 第一版不指定預排對應球場。
- 預排使用穩定 ID，顯示序號依位置計算。

預排 1 上場後，後方依序前移，自動模式可補算最後空位。

允許預排 2、3 跳過前方直接上場，但需確認會打亂順序。前方預排保持不動。自動模式正常派場時不得自行跳號。

### 10.10 多組智慧排點

- 同一次運算可依序計算多個空預排。
- 前一組人員從後續候選池排除。
- 優先確保最前方預排。
- 候選不足或接近逾時可只完成前方組別，不強求全部填滿。
- 不覆蓋團主已手動調整且仍有效的預排。

### 10.11 預排有效性與超時例外

球友在預排期間時間到：

- 立即變為無一般上場資格。
- 上場前必須再次驗證，不能只信任舊畫面。

自動模式：

- 強制尋找有效替補。
- 手動調整過的預排只替換失效位置，其他人保留。
- 若影響後續組別，從該組起依序重算後方。
- 只有完全沒有替補時才暫停該預排，讓團主選擇允許原球友本次上場、等待、移出或取消整組。

手動模式：

- 到期時提供更換、移出或「本次仍允許上場」。

一次性許可：

- 只綁定該預排／該場。
- 卡片顯示「時間已到・本次允許」。
- 移出預排即失效。
- 結算後不再進入候選池。
- 記錄授權者與時間。

### 10.12 球友部署

排點頁名單預設只顯示可排點者，排序預設等待輪數。

可切換顯示全部；不可排者降低視覺強度並顯示原因：尚未報到、HH:mm 開始、時間已到、休息、比賽中、已在預排。

選取最多四人後顯示：

- 加入下一個空預排（主要）。
- 選擇預排。
- 直接安排至空場。
- 取消選取。

少於四人可加入未滿預排；直接上場必須滿四人。

### 10.13 空球場選擇

- 自動模式依球場建立順序使用第一個空場。
- 手動只有一個空場時直接使用。
- 有多個空場時要求團主選擇。

### 10.14 語音叫號

- 格式：「[場地名稱]，請 [四位球友] 上場。」
- 正式叫號依瀏覽器原生佇列播放，不使用 `cancel()` 強制中斷。
- 測試語音可以獨立中斷測試。
- 切換自動模式時嘗試取得瀏覽器音訊播放權限。

## 11. 對戰紀錄與結算

### 11.1 建立與結算

正式安排上場時立即建立進行中紀錄，保存活動、球場 ID、球場名稱快照、四人、隊伍、開始時間、建立方式與來源預排。

結算時：

- 記錄結束時間與時長。
- 狀態改為已完成。
- 釋放球友並更新已打場數。
- 處理時間到期。
- 自動模式安排下一組。
- 不彈出比分視窗，只提供短暫「補登比分」。

### 11.2 對戰紀錄介面

- 排點頁頂部入口。
- 桌機右側抽屜、平板大型覆蓋面板、手機全螢幕次級頁。
- 第一版不提供篩選。
- 有效紀錄依時間新到舊顯示。
- 已取消紀錄收在列表底部的「已取消紀錄」區塊。

### 11.3 比分與結果

- 第一版只有單一比分，不支援局數。
- 每隊 0–99 整數。
- 不強制 21 分、勝兩分或正式規則。
- 比分非必填。
- 可只記結果：隊伍 A 勝、隊伍 B 勝、未分勝負、尚未記錄。
- 有比分時自動推導結果；同分為未分勝負。
- 不允許保存與比分矛盾的結果。

### 11.4 第一版可編輯內容

- 隊伍 A 分數。
- 隊伍 B 分數。
- 勝負結果。
- 對戰備註。

不編輯球友、隊伍、球場、開始／結束時間與時長。

### 11.5 取消本場與取消紀錄

進行中取消：

- 釋放球友。
- 不增加場數與重複統計。
- 不立即自動補位；該球場自動模式暫停一次。

已完成紀錄取消：

- 第一版無法復原。
- 狀態改為 `cancelled`，不永久刪除。
- 從場數與重複配對排除，系統需更新相關統計。
- 保留原比分與資料，移至已取消區塊。

### 11.6 重複配對統計

有效完成紀錄產生：

- 相同搭檔。
- 相同對手。
- 相同四人集合。

只使用本活動內已完成且未取消的對戰。不使用進行中、預排或已取消紀錄；第一版不跨活動累計。

## 12. 球團設定

### 12.1 設定架構

球團設定只保留三個主要頁籤：

- 一般設定：依序呈現球團資料、付款與串接、使用量與限制。
- 我的球館。
- 活動範本。

帳號與安全維持帳號層級的獨立設定頁，不混入球團設定。

球團設定的頁面功能列、頁籤及內容需與球團首頁共用主內容寬度與左側基準線。選取頁籤只以藍色底線表示；頁籤內容不使用整塊底色或卡片容器，以留白、標題及分隔線建立層級。一般設定不使用摺疊面板。

桌機版一般設定採「主要設定欄＋右側資訊欄」：主要設定欄維持適合閱讀與輸入的表單寬度，依序放置球團資料及付款與串接；右側資訊欄顯示使用量與限制，不得為填滿畫面而將輸入框拉至整頁寬度。窄螢幕改為單欄。各區塊標題與說明採同列的「標題＋小標」樣式，與球團首頁的區塊標題一致。

頁面功能列中的「球團設定」需以較高文字層級與頁籤區隔；三個頁籤緊接在頁面名稱後方，不靠齊工具列最右側。

設定表單沿用登入與註冊頁的深色輸入控制樣式。欄位名稱與必填星號必須位於同一行，星號不得形成獨立的版面列。表單主要 CTA 與欄位左側對齊，不使用置中或無必要的滿版按鈕。

第一版不顯示空白的成員與權限頁。

### 12.2 球團資料

- 球團名稱（必填）。
- 預設團主聯絡資料。
- 預設指定用球。
- 球團簡介。
- 第一版不提供圖片／Logo 上傳，使用預設圖示。

預設團主聯絡資料與指定用球在建立活動時帶入，之後由活動保存快照。

### 12.3 我的球館

欄位：名稱、縣市、行政區、地址、地板材質、備註、最近使用與使用次數。

功能：新增、編輯、複製、刪除、搜尋與排序。

刪除私人球館不影響既有活動快照。疑似重複時提示更新既有、仍新增或取消，不自動合併。

### 12.4 LINE Pay Demo

只做到可展示流程：

- Demo 商店名稱。
- 系統產生 Demo Merchant ID。
- 啟用／停用 Demo。
- 測試付款。

付款與串接的初始層級只顯示 LINE Pay Demo 啟用控制；啟用後才展開 Demo 商店名稱、Merchant ID 與測試付款操作。停用時隱藏這些從屬資料。

LINE Pay Demo 啟用控制不使用獨立底色或下方分隔線；展開的從屬欄位以縮排及左側導引線呈現階層。測試操作名稱為「測試付款」，結果需在操作附近立即顯示。

登入後所有原由右側滑入的編輯／設定面板統一改為畫面置中對話視窗；桌機寬度依內容控制、不得滿版，最大高度不得超過視窗可用高度，超出內容在視窗內捲動。背景遮罩及表單樣式沿用全域深色作業介面規範。

置中編輯視窗的標題列只保留主標題與右側關閉操作，兩者水平對齊；不重複顯示頁面小標或說明副標。視窗底色需比頁面內容區更深，表單欄位間距沿用登入／註冊表單的清楚分組節奏。

帳號設定頁沿用球團設定「一般設定」的內容基準、區塊標題／副標層級、深色輸入控制與 CTA 配置。活動範本清單在區塊說明下保留一條清單起始分隔線；範本名稱旁的筆形操作只負責重新命名，完整內容由列尾「編輯」進入。

建立／編輯活動三步流程沿用設定頁的內容密度與深色表單控制：桌機表單工作寬度限制在可閱讀範圍，不將欄位無限制拉滿；區塊標題與說明採同行層級，必填星號必須與欄位名稱同行。三步流程的輸入框、選單、Textarea、Hover 與 Focus 樣式一致。

不要求真實帳密、API Secret、合作商店審核資料，不實作正式串接後的卡控與連鎖檢查。

### 12.5 活動範本

顯示名稱、自訂活動標題、球館、各方案時段與金額、初始場地數、上場方式與更新時間。

功能：使用、編輯、重新命名、複製、刪除。第一版不限制範本數量。

### 12.6 使用量與限制

- 未封存活動數／5。
- 活動範本數。
- 私人球館數。
- 球團管理員數（第一版為 1）。
- 雲端同步狀態與最近同步時間。

不向一般團主顯示底層資料庫或 API 技術用量。

### 12.7 帳號與安全

第一版可查看帳號、修改顯示名稱與登出。修改密碼、重設密碼、登出其他裝置、匯出與刪除帳號保留選項但停用，標示「上線版」。

- 球館、地區、地址。
- 級數。
- 招收人數。
- 用球。
- 方案時間與金額。
- 注意事項與聯絡資訊。

未填欄位整行省略。提供複製文字、手機系統分享、編輯本次分享內容與恢復系統內容。本次文案編輯不回寫活動設定。

第一版不包含公開報名連結與球友名單。

### 13.4 匯出

活動操作選單提供：

- 匯出活動摘要：人類可閱讀／試算表用途。
- 匯出完整活動封存：包含設定、成員、報到、付款、預排、對戰、系統版本與匯出時間。

雲端資料為主要保存來源，匯出為備份與核對用途。

## 14. 響應式版面與視覺規範

### 14.1 斷點

- 桌機：≥ 1200px。
- 平板：641–1199px，10 吋橫向為主要優化目標。
- 手機：≤ 640px。
- 實際切換仍應依可用內容寬度驗證，不只依裝置名稱判斷。
- 設計與驗證權重依序為：平板、手機、桌機。

### 14.2 桌機

- 與平板共用可收合 Sidebar Shell 與內容元件。
- 登入後工作區採可用寬度優先；一般桌機頁面的實際內容上限為 **1040px**，排點作業可使用全部可用寬度。不得由個別一般頁面任意建立互不一致的上限。
- Shell 可包含左右 24px 內距；資料密集工作頁應優先保留橫向辨識空間。
- 名單優先使用表格或資料列；需要快速掃讀、選取或觸控操作時可使用單層卡片模式。
- 球場／預排依可用寬度排列，個別項目保留清楚的操作邊界；所屬大型工作區可使用單層區塊容器，但不得再以相同視覺重量重複包裝。
- 名單情境工具列在名單上方。
- 對戰紀錄右側抽屜。

### 14.3 平板

- **1024 × 768 橫式平板為第一優先設計與展示尺寸**；直式平板依手機與窄版工作區規則重排。
- 側欄預設收合，展開時覆蓋內容。
- 活動頁籤固定於內容頂部，不使用底部全站導覽。
- 名單約 3–4 卡一列。
- 球場／預排約 2–3 卡一列。
- 報到選取工具列固定底部。
- 對戰紀錄為大型覆蓋面板。

### 14.4 手機

- 頂部列＋滿版全域選單；帳號操作放在滿版選單底部。
- 活動內頁籤位於內容頂部：總覽／名單／排點。
- 排點頁內次級頁籤：球場／預排／球友。
- 球場為排點頁預設頁籤。
- 選取球友後底部顯示部署工具列。
- 部署完成後切換到對應預排或球場並短暫高亮。
- 手機版保留完整後台操作能力，不得只提供唯讀或功能刪減版。
- 桌機的大型表格在手機改為摘要資料列；點擊或展開後顯示完整欄位與操作，不以水平捲動作為主要方案。
- 不依賴拖曳與 Hover。

### 14.5 觸控與文字

- 觸控熱區至少 44 × 44px。
- 姓名為球友卡最重要資訊，不因其他徽章被壓縮。
- 可點擊功能不可只靠顏色辨識。
- 手機輸入欄位文字至少 16px，避免瀏覽器縮放。
- 桌機與平板的一般按鈕及輸入控制高度以 40px 為基準；手機重要觸控操作仍須提供至少 44 × 44px 的有效熱區。

### 14.6 色彩

- 第一階段採明亮淺色介面；中性灰階負責背景、表面、結構與文字，避免全白區塊失去層級。
- 明亮競技藍／寶藍作為產品主色，用於主要 CTA、選取、Focus、目前頁籤、連結與重要導覽狀態。
- 綠色嚴格只代表成功／已完成／已付款／可匯入等正向結果，不得用於品牌文字、一般標題、底色裝飾、主要 CTA 或一般選取狀態。
- 黃色與橙色代表待處理、警告、休息或競賽中的注意焦點。
- 紅色代表錯誤、破壞性操作、避免同場、落後或需介入；競賽語意不得只靠色彩表達。
- 尚未開始與進行中使用藍色系狀態；草稿、已結束與已封存使用中性灰階，不因「進行中」而使用成功綠色。
- 球場卡中性；預排卡以標題／邊框作區隔。

正式色彩 Token：

| Token | 色碼 | 用途 |
| :--- | :--- | :--- |
| `color-primary` | `#1D5FD1` | 主要 CTA、選取、Focus、連結 |
| `color-primary-hover` | `#174EAE` | 主要操作 Hover／強調 |
| `color-primary-soft` | `#E8F0FF` | 淺色選取底與焦點提示 |
| `color-text` | `#172033` | 主要文字 |
| `color-muted` | `#667085` | 副標、欄位名稱、輔助資訊 |
| `color-line` | `#D8DEE9` | 邊框與分隔線 |
| `color-background` | `#F4F6FA` | 登入後工作區背景 |
| `color-surface` | `#FFFFFF` | 主要表面與輸入框 |
| `color-surface-subtle` | `#EEF2F7` | 次要區塊、表頭與摘要底色 |
| `color-navigation` | `#FFFFFF` | 第一階段全域導覽背景；以邊框與淺藍選取狀態建立層級 |
| `color-success` | `#21865A` | 成功／完成狀態 |
| `color-warning` | `#C77912` | 警告／待處理／空場 |

實作時必須引用語意 Token，不得在頁面元件中另建 `green-*`、`brand-green` 或其他品牌色變數。後續暗色模式應覆寫同一組語意 Token，不得複製一套頁面元件或在個別頁面硬編碼主題色。

### 14.7 視覺風格

- 正式方向為「專業賽事管理後台帶有運動性」：以清楚、可用、可預期的管理介面為主體，透過比分、狀態、節奏、重點數字與少量方向性細節加入競技張力。
- 運動感不得依賴大面積螢光色、滿版漸層、羽球圖案或速度線裝飾；應優先來自資訊節奏、對比與現場狀態表達。
- 第一階段完成淺色模式；結構、字體、排版與元件均需可套用後續暗色 Token，不得只以反相色彩模擬暗色模式。
- 第一階段的登入／註冊、全域導覽、內容工作區、現場工作台與其操作元件均採淺色表面；不得保留局部深色面板作為視覺強調。競技張力以寶藍主色、狀態色、數字與版面節奏呈現。
- 使用中小型圓角，避免可愛或玩具感；圓角用於整合容器和操作，不以元件形狀限制按鈕層級。
- 卡片不是禁用元素。卡片用於區分大型功能區塊、摘要模組或具獨立操作／狀態邊界的資料單位；卡片內部以字級、字重、間距、對齊、底色與必要分隔建立層級。
- 避免大卡片、中卡片與小卡片以相同邊框、底色或陰影層層嵌套；若第二層元素沒有獨立操作或狀態邊界，應移除其完整外框。
- 陰影低存在感或不使用；不使用大面積漸層、Glassmorphism 與大模糊陰影。
- 內文預設字重 400；按鈕與標籤以 400–500 為主；頁面及區塊標題以 500–600 為主，避免整頁大量使用 700 粗體。
- 中文正文使用 `Noto Sans TC`；場地編號、計時、日期、金額及對齊數字使用等寬數字字型；品牌縮寫可使用窄體斜體字形建立運動識別。
- 羽毛意象 Logo 以向量／程式資產呈現；第一版不提供球團圖片上傳。
- 「羽點通」目前沒有正式 Logo、品牌字體或品牌色資產；正式識別完成前不得自行加入英文副標。暫用圖形標誌僅作系統識別，不視為定案 Logo。

頁面依任務採少量、明確的模板，不要求所有頁面同形：

1. **列表管理頁**：頁首、主要 CTA、篩選／工具列、表格或摘要資料列、分頁。
2. **詳情／總覽頁**：頁首與狀態、必要摘要、主要內容區塊、次要資訊與管理操作。
3. **建立／編輯流程**：步驟或頁首、分段表單、固定且可預期的主要與次要操作。
4. **現場工作台**：精簡識別、即時控制、球場／預排／名單主工作區、情境操作列。

相同功能、層級與狀態必須跨模板沿用相同元件及視覺語意；不同任務可調整布局與資訊密度。

### 14.8 文字層級與頁首

- 頁面主標題：26px、字重 600、行高約 1.25。
- 區段標題：18px、字重 600。
- 子區段標題：15px、字重 600。
- 一般正文與資料：14px、字重 400。
- 欄位名稱、副標與輔助文字：12–13px、字重 400–500。
- 登入後頁面固定分為左側全域導覽與右側內容工作區。內容工作列承載目前工作對象、子頁籤及頁面主要操作。所有登入後頁面的內容工作列共用主內容寬度、68px 高度與相同文字層級；返回圖示、頁面名稱及頁籤必須共享同一垂直中心。頁面名稱使用較高字重，頁籤緊接其後，頁面操作則靠右排列。
- 活動完整日期、時間及場館只在活動概況介紹面板呈現；名單與排點只保留精簡活動名稱，避免現場工作頁重複資訊。
- 主標題描述當前工作對象；副標只放日期、時間、地點或簡短上下文，不重複主標題。
- 活動狀態放在活動主標題旁，不放在標題前方，也不得搶過主標題的視覺權重。
- Eyebrow 僅用於側欄、對話框或需要補充上下文的區域，不在每個頁首固定重複球團名稱。

### 14.9 CTA 與操作層級

- 每個頁面或工作區原則上只設定一個主要 CTA；使用實心藍色按鈕。
- 次要 CTA 使用白底、中性邊框；低頻操作使用文字按鈕或收進 Material Icon「更多」選單。
- 破壞性操作使用紅色語意，不得使用主要藍色或成功綠色。
- CTA 文案應直接描述結果，例如「建立新活動」「匯入名單」「進入排點作業」，避免只寫「確認」或「送出」。
- 球團首頁主要 CTA 為 Banner 標題列中的「建立活動」；範本區塊的各範本是快速建立入口。活動資料列外顯主要 CTA 只保留「進入活動」，複製、封存、刪除等收進更多選單。
- 活動詳情頁的頁首 CTA 依活動狀態切換：尚未開始前前往「名單與報到」、進行中前往「排點作業」、已結束前往紀錄檢視。
- 「名單與報到」工作區以「匯入名單」為主要 CTA，「新增球友」為次要 CTA。

### 14.10 表單與輸入欄位

- 一般欄位固定使用兩行結構：第一行欄位名稱與紅色 `*`（必填時），第二行輸入控制；不得常駐第三行提示文字或字數計數。
- 一般文字欄位 Placeholder 統一採合法內容範例，格式為「例如：週三消夜團」。
- 下拉選單空值統一為「請選擇⋯⋯」；搜尋欄可使用「輸入姓名搜尋」等動作型文案。
- 登入欄位使用「輸入帳號名稱」「輸入密碼」；註冊帳號與密碼可在 Placeholder 或錯誤狀態顯示必要格式規則。
- 不混用「例如」「限制 1–30 個字」「請輸入地址」三種一般提示策略。字數限制由 `maxLength` 實作，只有帳號／密碼等特殊格式需要預先說明。
- 錯誤與驗證訊息只在錯誤發生後顯示於欄位附近；不得以常駐紅色說明增加畫面噪音。
- 活動時間統一使用 24 小時制；跨日活動需明確顯示次日，不得切回 12 小時制。
- 活動標題、球館名稱、指定用球、聯絡資料、備註、帳號名稱、顯示名稱、球團名稱與密碼皆需設定合理字數上限。

### 14.11 間距、容器與卡片使用

- 基礎間距 Token：4、8、12、16、24、32、40、48px；新增頁面不得任意加入 18、22、26、28、30px 等非 Token 間距。
- 中等偏緊湊密度的量化基準：桌機／平板一般控制高度 40px、表格資料列 44–48px、摘要列 52–64px、一般區塊內距 20–24px、緊湊操作單位內距 12–16px；手機核心觸控熱區不得小於 44px。
- 頁首到頁籤 16–24px；頁籤到主要內容 24–32px；大區段之間 24–32px；區段標題到內容 12–16px。單一模板內取值必須一致，不得逐區微調。
- 一般控制元件圓角 6–8px；大型區塊容器以 8–12px 為基準。資料列、表格及卡片可依角色使用不同圓角，但相同層級必須一致。
- 大型卡片可用於劃分頁面的主要功能區；KPI、圖表、待辦、球場、預排與摘要可依內容關係使用單層卡片或模組化網格。
- 大型區塊內的細節優先以字級、間距、對齊、底色、資料列、Description List、表格及必要分隔線組織，不再讓每個數字、欄位或操作各自擁有完整卡片外框。
- 不允許純裝飾性的多層巢狀卡片。只有內層項目本身可獨立操作、選取、展開或具有明確狀態邊界時，才可建立第二層容器，且其視覺重量必須低於外層。
- 統計摘要可依比較需求使用並列 KPI 卡；相關數字若需共同解讀，應整合在同一摘要模組，不為增加造型而拆分。
- 同類容器內距、邊界與標題位置必須一致；卡片、表格和分隔線均為可選工具，不預設任何一種永遠優先。

### 14.12 活動詳情頁專用規範

- 頁籤固定為「活動概況／名單與報到／排點作業」。
- 活動概況依第 7 章使用「報名與出席」「帳務與付款方式」「方案與各時段人數」三個儀表板模組；不另設重複的「活動資訊」或「方案與帳務」區塊。
- 名單表格可置於單一大型資料區塊內，但不得再為表頭、每列或每個欄位建立同等重量的巢狀卡片。
- 排點頁的球場與預排為同一個連續工作區，所有一般球場之後直接接續預排；「可排點球友」以清楚的區段標題、間距或表面差異區分，不強制只使用水平分隔線。個別球場與預排隊列保留明確操作容器。
- 排點頂部工具列放置「自動模式」Switch、「排點設定」與「對戰紀錄」，不再另設重複控制列；如使用工作區容器，工具列應成為同一區塊的標題列而非額外浮起卡片。
- 球場與預排數量在工作區標題右側分組呈現，兩組均提供增減控制，避免混淆資源類型。
- 比賽中場地表頭固定顯示兩位數場地編號、由 `00:00` 開始的經過時間與「比賽中」狀態；四位球友以固定 2 × 2 位置顯示姓名與級數。
- 比賽中球友位置不使用虛線；只有空場位置與預排位置使用虛線，表達尚未上場或可調整。
- 場地底部固定呈現「設定」齒輪、「再次叫號」廣播器，以及主要操作「結束本局」；不使用更多選單圖示作為入口。
- 預排接續一般場地出現在同一工作流，不另起獨立橫排；以黃色頂線與 `NEXT` 標記區隔，不使用暖灰底。
- 預排底部操作為次要按鈕「重算預排」與主要按鈕「一鍵上場」；僅有多個空場時才要求指定球場。預排卡片與球場卡片在同一列時維持一致高度。
- 「結束活動」屬活動生命週期的高風險管理操作，只放在活動概況的活動管理區，不得出現在排點工具列或場地工作區。

### 14.13 圖示規範

- 系統圖示可使用 Google Material Icons 的 SVG Path／程式資產形式，並由共用 `MaterialIcon` 元件管理。
- 不要求使用者額外下載字型檔；第一版不得依賴外部 Icon Font 才能顯示核心操作圖示。
- Icon 用於導覽、操作、狀態與高頻資訊辨識，不作為每個標題或卡片的固定裝飾。
- 重要操作以「Icon＋結果型文字」為主；只有關閉、更多、側欄收合、增減等普遍理解且空間受限的低風險操作可只顯示 Icon。
- 資訊、成功、警告與錯誤分別使用固定且一致的語意 Icon；顏色必須搭配 Icon 與文字，不得只靠色彩傳達結果。
- 活動日期、時間、球館、場地數與名單人數可在摘要列使用 16–18px Icon 協助掃讀；表格欄位已清楚時不得在每格重複相同 Icon。
- 導覽 Icon 20px、按鈕 Icon 18–20px、輔助資料 Icon 16–18px、Toast／Banner Icon 20–24px、完成或空狀態 Icon 32–48px。
- 不使用 Emoji 取代正式系統圖示，也不得在同一介面混用多套線條或填色風格。
- 只顯示圖示的按鈕必須提供可讀的 `aria-label`，且觸控熱區符合 14.5。

### 14.14 系統回饋、提醒與確認

系統回饋依影響範圍分為五層，不得以同一種訊息框混用載入、資訊、警告、錯誤與成功：

1. **欄位錯誤**：可在單一欄位修正的問題顯示於欄位下方，欄位同步顯示錯誤狀態；提交後聚焦或捲動至第一個錯誤。只有跨欄位問題才在欄位群組上方補充摘要。
2. **區塊 Banner**：持續影響目前工作區的資訊、警告或錯誤。必須包含語意 Icon、簡短標題、必要說明；有可行解法時直接提供「重新整理」「查看名單」等操作。一般儲存成功不得使用大型 Banner。
3. **Toast**：用於不需下一個決策的短暫操作結果，例如儲存、複製、新增、報到與批次更新。桌機／平板位於右上，手機位於畫面下方並避開安全區與固定操作列；不得造成內容位移。
4. **確認 Dialog**：所有刪除，以及取消報名、取消對戰、關閉自助報到等具有資料或流程後果的操作，執行前使用統一 Dialog；不得使用瀏覽器原生 `window.confirm`。標題、說明與按鈕均描述實際結果，不使用籠統的「確定」。
5. **完成／阻擋狀態**：只用於流程正式結束或無法留在原工作區繼續操作，例如報到完成、連結失效、無權限或核心資料無法載入；必須提供下一步或重試入口。

回饋語意與行為：

- 藍色為資訊、橙色為警告、紅色為錯誤、綠色為成功；四者均需搭配固定 Icon 與文字。
- 成功 Toast 預設 3–4 秒自動消失；錯誤 Toast 保留 6–8 秒並可手動關閉。影響整個工作區的錯誤改用 Banner，不依賴 Toast。
- 同時最多顯示 3 則 Toast；重複訊息應合併或取代，並透過 `aria-live` 宣告結果。
- 若操作結果已在畫面中明確呈現，可不額外顯示成功 Toast；不得為每個成功操作加入大型綠色提示。
- Loading 不屬於 Alert；使用骨架、中性載入狀態或按鈕處理中文字，不得套用錯誤或警告樣式。
- 批次操作回饋應包含處理數量與結果。錯誤文案依「發生了什麼、影響為何、接下來可做什麼」撰寫，避免只寫「操作成功」「發生錯誤」。
- 破壞性 Dialog 的確認按鈕使用紅色語意與結果型文案，例如「刪除活動」「取消本場」；取消或返回為次要操作。

### 14.15 後續開發與驗收門檻

本節為後續所有新頁面、功能修正與重構的強制規範。實作前應先重用既有 Token 與共用元件，不得由單一頁面重新定義品牌色、版寬、按鈕或輸入框樣式。

每次新增或修改頁面至少檢查：

1. 桌機實際內容最大寬度是否維持 1040px，切頁左右邊界是否一致。
2. 主標題、副標、狀態與主要 CTA 的順序和層級是否符合 14.8、14.9。
3. 是否只有一個主要 CTA，其他操作是否降為次要或更多選單。
4. 綠色是否只用於成功／完成狀態，且沒有新增舊綠色硬編碼。
5. 表單是否維持兩行結構、Placeholder 策略一致、必填紅色 `*` 與字數上限完整。
6. 間距是否只使用 Token，同類容器內距是否一致。
7. 卡片是否只建立必要的大區塊或獨立操作／狀態邊界，且沒有相同重量的容器層層嵌套。
8. 區塊內是否以文字、間距、對齊、資料列、表格或必要分隔建立清楚層級，而非替每個元素增加完整外框。
9. 相同頁面模板的頁首、工具列、CTA、資料區與容器規格是否一致；跨模板的相同功能是否重用相同元件。
10. 資訊密度是否符合 14.11 的尺寸範圍，且同一模板沒有任意混用寬鬆與緊湊間距。
11. 是否在 360px 手機、768px 平板與 1280px 桌機驗證，沒有依賴 Hover，且手機保留完整操作能力；大型表格是否轉為可展開摘要列。
12. 回饋是否依 14.14 選用正確層級，沒有混用語意、使用原生確認框，或以 Loading 假裝 Alert。
13. Icon 是否用於辨識而非裝飾，且重要操作保留清楚文字、純 Icon 按鈕具有 `aria-label`。
14. 是否通過與變更風險相符的 TypeScript、Lint、測試與建置檢查。

若新需求與本章衝突，必須先更新 PRD 並取得設計決策，再進入程式實作；不得以單頁例外默默偏離規範。

## 16. 權限、資料一致性與非功能需求

### 16.1 權限

- 球團管理權限依 `OrganizationMembership.role` 判斷，不依帳號 Profile 的固定角色判斷。
- 第一版僅 owner 可讀寫其擁有球團的管理資料；未來 admin 依權限設定取得管理能力。
- 沒有對應 Membership 的登入帳號，不得因能使用球友前台而取得球團管理資料。
- 公開自助報到只能透過有效 Token 存取最小必要資料。
- 公開流程不能取得團主備註、關係、完整付款明細與帳號資料。
- 所有資料庫存取需套用 Row Level Security 或同等後端授權。

### 16.2 即時同步

自助認領、Demo 付款與團主報到頁需即時同步。認領需使用原子條件更新，避免同一人被兩台裝置同時認領。

### 16.3 資料一致性

- 已付款批次操作不得覆蓋既有付款方式。
- 比賽中球友不可被取消、改方案或設休息。
- 同一球友不可同時存在於多個球場／預排。
- 上場前必須重新驗證候選資格。
- 取消對戰後需更新場數與重複配對統計。
- 刪除球友或關係時需清除外部殘留引用。

### 16.4 效能

- 一般 20–40 人活動的主要操作需保持流暢。
- 排點運算不得阻塞主執行緒。
- 列表需避免因每次輸入或計時器更新重繪所有卡片。
- Realtime 訂閱需以活動為範圍，不全域監聽所有球團資料。

### 16.5 離線與失敗

- 顯示雲端同步狀態。
- 暫時斷線時避免靜默遺失操作。
- 高風險寫入在失敗時需復原畫面狀態並提示重試。
- 排點、結算與付款不可只依樂觀畫面更新而不確認後端結果。

### 16.6 可及性

- 所有主要操作可使用鍵盤完成。
- 不以長按作為唯一不可替代入口；正好選取一人時提供查看詳情。
- 圖示按鈕需有可存取名稱。
- 狀態不可只依賴顏色。
