# Badminton Match Master｜專題 Demo 系統介紹

> 專案名稱：Badminton Match Master（產品暫定名稱：羽你有約）  
> 專案類型：羽球零打活動、報到、帳務與排點管理 Web App  
> 主要使用者：羽球零打團團主、球隊管理者  
> Demo 版本：V0.1／PRD V2.4  
> 文件更新：2026-09-02

## 一句話介紹

Badminton Match Master 是一套為羽球零打團主設計的現場營運控制台，把原本散落在 LINE 接龍、紙本名單、收款紀錄與團主腦中的排點判斷，整合成一個可在桌機、平板與手機操作的系統。

## 專案緣起：我想解決的真實問題

羽球零打活動開始前後，團主通常必須同時處理多件事：整理 LINE 接龍名單、確認方案與費用、核對報到及收款、安排程度相近的四人上場、記住誰等最久與誰剛打完，還要在吵雜的球館叫人上場。

這些工作往往依賴紙筆、試算表、聊天室與個人記憶。人數一多，資訊便容易不同步，也容易出現漏收費、重複排到同一人、等待時間不公平，或團主忙著處理行政而無法專心打球的情況。

因此，本專題不是從「可以做什麼技術」出發，而是從熟悉的羽球零打場景出發，將團主從開團到活動結束的工作流程做成真正可操作的產品。

## 目標使用者與 User Story

### 主要使用者：零打團團主

- 身為團主，我希望快速建立活動、方案、費用與球場資訊，避免每次開團重複設定。
- 身為團主，我希望直接匯入 LINE 接龍名單並在現場完成報到與收款，避免紙本核對與事後重新對帳。
- 身為團主，我希望系統依等待時間、已打場數、程度與配對關係提出排點建議，降低排點的認知負荷與公平性爭議。
- 身為團主，我希望清楚掌握球場、預排、候選球友與比賽狀態，能在突發狀況下人工調整。
- 身為團主，我希望保留活動、付款與對戰紀錄，方便結算、回顧與複製下一場活動。

### 次要使用者：到場球友

- 身為球友，我希望掃描 QR Code 後直接從名單認領自己，不必先註冊帳號。
- 身為球友，我希望完成 Demo 付款與報到，減少在入口等待團主逐一處理的時間。
- 身為球友，我希望排點規則更透明，降低等待過久或配對強度落差過大的情況。

## 系統如何解決問題

| 現場痛點 | 系統解法 | 帶來的價值 |
| --- | --- | --- |
| 開團設定重複、資訊散落 | 三步式建立活動、常用球館、活動範本與複製功能 | 減少重複輸入，讓活動資料格式一致 |
| LINE 接龍名單難整理 | 支援名單新增與文字匯入，檢查重複姓名、級數與方案 | 降低人工謄寫錯誤 |
| 報到、方案與付款各自記錄 | 名單、報到、付款狀態與帳務摘要集中管理 | 現場狀態與事後結算使用同一份資料 |
| 團主必須靠記憶排點 | 依等待、場數、級數、性別偏好與成員關係產生建議 | 降低認知負荷，提升排點公平性 |
| 球場與預排容易失去同步 | 球場、數組預排、可排名單與比賽狀態置於同一工作區 | 團主可快速掌握下一步 |
| 現場叫人不易 | 支援瀏覽器語音叫號設定與測試 | 減少反覆找人、喊人的負擔 |
| 尖峰時段報到塞車 | QR Code 自助認領與 LINE Pay Demo 流程 | 將部分報到工作交由球友自行完成 |

## 目前可展示的核心功能

### 1. 帳號與展示模式

- 帳號名稱與密碼註冊、登入及登出。
- 建立帳號時同步建立個人資料、球團與 Owner 身分。
- 訪客展示模式：不需要正式帳號即可使用固定示範資料體驗主要流程。
- 帳號設定可查看帳號並修改暱稱。

### 2. 球團首頁與活動生命週期

- 依「進行中、即將開始、草稿、已結束、已封存」篩選活動。
- 顯示活動日期、時間、球館、場地數與名單人數。
- 管理未封存活動使用量，達上限時引導封存或刪除草稿。
- 支援複製、封存、解除封存及草稿／封存活動刪除。

### 3. 三步式活動建立

1. 設定日期、球館、場地數、招收人數、級數範圍與上場方式。
2. 設定最多五種參與方案、跨午夜時間、費用與付款方式。
3. 確認活動摘要、語音叫號等現場設定後建立活動。

系統也支援常用球館、活動範本、複製既有活動與編輯活動，讓固定開團不必重複輸入相同資料。

### 4. 名單、報到與帳務

- 新增單一球友或批次匯入接龍文字。
- 管理姓名、級數、性別、方案、在場狀態與備註。
- 支援批次報到、收款、付款方式記錄與後續更正。
- 顯示應收、已收與待收資訊，保留未到或免追款等例外處理。

### 5. 排點與球場管理

- 同一工作區呈現球場、數組預排與可排球友。
- 支援系統建議、人工選取、直接安排上場及自動排點模式。
- 排點條件納入級數落差、等待時間、已打場數、男女／混雙偏好與重複配對。
- 支援兩人同隊綁定、單場同隊、單場對戰與避免同場等關係條件。
- 可新增、重新命名或移除球場，並處理預排超時與人工覆寫。
- 比賽結束後可記錄比分、勝負與對戰歷程。

### 6. QR Code 自助報到與 Demo 付款

- 團主可開啟活動自助報到並產生 QR Code。
- 球友免登入即可選擇並認領自己在活動名單中的身分。
- 球友確認方案後進入 LINE Pay 模擬付款流程；Demo 不會產生真實扣款。
- 完成後同步更新付款與報到狀態，並設計避免重複認領與重複付款的資料流程。

### 7. 球團設定

- 編輯球團名稱、簡介、預設聯絡資訊與指定用球。
- 管理私人常用球館與活動範本。
- 啟用、設定與測試 LINE Pay Demo 商店。

## 智慧排點不是「讓 AI 隨機選四個人」

本系統的排點重點是把團主原本存在腦中的判斷條件資料化，再以可驗證的規則產生候選組合。系統會綜合考量：

- 球友是否已報到、暫離或正在比賽。
- 方案是否已開始或已超時。
- 等待時間與已完成場數。
- 四人級數落差與對戰強度。
- 男女雙、女雙與混雙偏好。
- 過去同隊／對戰組合的重複程度。
- 團主設定的綁定與避免同場關係。

最後決策權仍保留給團主。系統提供建議、自動模式與人工覆寫，而不是在例外很多的現場情境中完全取代人。

## AI 在專案中真正做了什麼

AI 不只用來撰寫介紹文字，而是參與完整開發循環：

1. **需求整理**：將田調、使用者痛點與競品觀察整理為 User Story、產品範圍與可驗收規則。
2. **規格收斂**：協助辨識需求衝突，例如手機拖曳的可用性、金流 Demo 與真實交易的界線、帳號和球團身分的關係，並持續修訂 PRD。
3. **介面與流程實作**：依 PRD 建立 React 頁面、響應式版面、表單驗證、活動工作區與訪客展示資料。
4. **資料與安全設計**：協助建立 PostgreSQL schema、RLS、交易型 RPC、登入 Edge Function，以及 QR Code token、認領與付款的狀態流程。
5. **問題拆解與修正**：將開團、報到、排點與結算拆成可獨立驗證的模組，根據實際操作結果持續修正資訊架構與互動方式。
6. **測試與文件**：產生並執行型別、Lint、單元測試與建置檢查，同步維護 PRD、技術架構與操作說明。

我的角色不是把需求全部交給 AI，而是提供場域知識、判斷問題優先順序、確認產品決策與驗收結果；AI 則加速資料整理、方案比較、程式實作、測試與重構。這個合作方式讓開發速度提升，同時仍由人對需求合理性與最終品質負責。

## 從第一版到目前版本的迭代

專案保留了舊版 PRD、研究資料與逐步新增的資料庫 migration，可追溯需求及實作如何演進。幾個具代表性的調整如下：

| 初期想法 | 操作／設計發現 | 現行決策 |
| --- | --- | --- |
| 以單一長表單建立活動 | 設定項目多，使用者難以確認進度 | 改為基本資料、方案帳務、確認設定三步流程 |
| 以 LocalStorage 作為主要資料 | 無法支援跨裝置、權限與現場同步 | 改為 Supabase Auth、PostgreSQL、RLS 與交易 RPC |
| 在排點頁使用拖曳卡片 | 手機不易精準拖曳，也不利無障礙操作 | 第一版改為點擊選取與情境工具列 |
| 單一預排 | 現場需要預先安排不只下一組 | 改為有順序的多組預排，並允許跳組上場 |
| 以時間自動結束活動 | 球館現場經常延長，時間不等於實際結束 | 到時自動開始，但必須由團主手動結束 |
| 直接串接真實金流 | Demo 階段有交易、憑證與法規風險 | 明確標示 LINE Pay Demo，只模擬成功、不扣款 |
| 桌機版縮小即為手機版 | 排點資訊密度過高，手機畫面難以操作 | 為手機規劃次級頁籤與底部操作區 |

這些變更顯示本專題不是一次生成的畫面，而是從問題、規格、原型、實作到驗證逐步收斂的產品。

## 技術架構

- **前端**：React 19、TypeScript、Vite、React Router、TanStack Query。
- **後端**：Supabase Auth、PostgreSQL、Row Level Security、Database RPC、Edge Functions。
- **同步策略**：資料庫為單一真實來源，前端快取只負責顯示加速；架構保留 Realtime 即時同步能力。
- **安全策略**：密碼交由驗證服務保存；登入轉接、公開自助報到與需使用密鑰的操作由 Edge Function 處理；關鍵跨表操作透過資料庫交易避免狀態只完成一半。
- **響應式設計**：平板優先，同時支援 360px 手機、768px 平板與 1280px 桌機；核心操作不依賴 Hover 或拖曳。
- **展示能力**：未設定 Supabase 時可進入本機訪客展示模式，便於面試或成果展示。

## 測試與驗證方式

目前專案的基本品質檢查包含：

- `pnpm typecheck`：檢查 TypeScript 型別。
- `pnpm lint`：檢查程式風格與常見問題。
- `pnpm test`：驗證 App Shell、活動表單規則與名單匯入解析等行為。
- `pnpm build`：確認可產出正式部署版本。
- 響應式驗收：至少檢查 360px、768px、1280px，並確認核心操作不依賴 Hover。
- 資料層驗收項目：包含跨球團權限、活動上限、跨活動資料完整性、同一球友／球場不可重複進行比賽，以及跨午夜方案等情境。

Demo 時應誠實區分「已由自動化測試覆蓋」、「已人工操作驗證」與「規格已定義、仍待完整整合驗證」三種狀態，不以畫面可點擊取代流程與資料正確性的證明。

## 建議 Demo 流程（約 6–8 分鐘）

1. **問題情境（約 45 秒）**  
   說明團主如何在 LINE、紙本、收款與排點之間切換，以及公平性和認知負荷問題。

2. **從球團首頁建立活動（約 1 分鐘）**  
   展示活動狀態、使用量、範本，以及三步式活動建立中的球館、方案、費用與付款方式。

3. **匯入名單與辦理報到（約 1.5 分鐘）**  
   貼入一段模擬 LINE 接龍資料，展示解析、錯誤提醒、批次報到與付款記錄。

4. **進入排點工作區（約 2 分鐘）**  
   說明球場、預排與候選球友，產生一組建議，人工調整後安排上場，再完成比賽及記錄比分。

5. **切換球友視角（約 1 分鐘）**  
   掃描 QR Code，認領名單、確認方案並完成 LINE Pay Demo 付款與報到。

6. **收尾（約 45 秒）**  
   回到團主畫面確認狀態已同步，說明 AI 如何參與需求、實作、測試及迭代，而最終決策仍由開發者負責。

## Demo 開場口述範例

> 我做的是一套羽球零打團主的現場管理系統。實際開團時，團主常常同時看 LINE 接龍、紙本名單、付款紀錄，還要記誰等最久、誰剛打完、哪些人的程度適合。這個專題把這些分散工作整合成一個可操作的 Web App。今天我會示範從建立活動、匯入名單、報到收款，到排點、比賽結算，以及球友掃碼自助報到的完整流程。AI 在這個專案中不只幫我寫文件，而是參與需求拆解、資料結構、功能實作、測試和多次迭代；我則負責提供真實場景、做產品決策並驗證結果是否真的能解決問題。

## 專案價值與後續發展

目前成果已是一個能展示核心流程的真實系統，而不是只有介面稿或提案簡報。它展現了：

- 從熟悉場域辨識問題並轉換成產品需求的能力。
- 與 AI 協作完成規格、架構、程式、測試及文件的能力。
- 在功能、現場可用性、資料一致性與安全之間做取捨的能力。
- 透過版本化規格和 migration 持續迭代，而非一次性完成作業的開發方式。

後續可發展的方向包括球友正式帳號與公開報名、多人共同管理球團、球友手機即時看板、歷史表現與出勤分析，以及場地預約整合。這些功能可沿用目前的帳號、球團、活動與成員關聯架構繼續擴充。

## 現階段邊界

- LINE Pay 僅為 Demo 模擬流程，不會產生真實交易。
- 第一版主要管理角色為單一球團 Owner；多人管理的資料角色已預留，但介面尚未開放。
- 公開活動探索、一般球友正式註冊報名、完整推播與場地預約屬後續發展項目。
- Demo 結果應以當前部署環境與實際驗證狀態為準。
